# 后续云服务与产品亮点规划

这份文档记录当前域名购买时顺带出现的云服务，以及它们和知识编排平台后续能力之间的关系。

目标不是“看到优惠就都买”，而是判断：

- 哪些现在值得低成本占位
- 哪些以后能真正变成产品亮点
- 哪些只是和当前系统无关的搭售
- 后续如果接入，代码和架构应该怎么演进

---

## 1. 当前购买建议

如果当前页面可选项包括：

- COS 标准存储 100G / 1 年
- 基础图片处理 1TB / 1 年
- 轻量对象存储 10GB / 1 年
- 企业网盘 60GB / 1 个月
- CDN 流量包

建议选择：

| 服务 | 建议 | 原因 |
| --- | --- | --- |
| COS 标准存储 100G / 1 年 | 建议购买 | 和文档库、图片附件、文件备份、对象存储化最匹配 |
| 基础图片处理 1TB / 1 年 | 低价可买 | 如果确实只要 1 元左右，可以作为后续图片压缩、缩略图、水印的试验资源 |
| 轻量对象存储 10GB / 1 年 | 不建议 | 和 COS 定位重叠，容量和流量都偏小，容易造成双存储体系 |
| 企业网盘 60GB / 1 个月 | 不建议 | 是独立网盘产品，不能自然进入当前 RAG / 文档库链路 |
| CDN 流量包 | 暂不建议 | 当前访问量不大，前端和文档下载先走服务器；后续公网访问量上来再买 |

当前最推荐组合：

```text
域名 kopai.work
+ COS 标准存储 100G / 1 年
+ 基础图片处理 1TB / 1 年，仅在价格极低时保留
```

更保守的组合：

```text
域名 kopai.work
+ COS 标准存储 100G / 1 年
```

## 2. 最值得保留的未来亮点

### 2.1 文档资产对象存储化

对应服务：

- COS 标准存储

当前项目的文件主要在服务器本地：

```text
data/user_docs/{user_id}/{folder_id}/...
```

后续可以升级成：

```text
文档上传
├─ 文件写入 COS
├─ MySQL 保存 object_key / size / mime_type / checksum
├─ 索引任务从 COS 下载或流式读取文件
├─ 解析、切片、向量化、写入 Chroma
└─ 前端预览 / 下载时使用临时签名 URL
```

产品亮点可以写成：

- 文档资产云端化存储
- 计算容器和文件存储解耦
- 支持服务器迁移后保留统一文档资产
- 支持后续多服务器部署共享同一份文件
- 支持文档下载、备份、归档和生命周期管理

技术价值：

- 不再把所有文件绑死在单台云服务器磁盘上
- 容器重建、服务器迁移、磁盘扩容时风险更低
- 后续做多实例部署时，后端实例可以共享同一个对象存储

优先级：

```text
高
```

---

### 2.2 图片附件云端化

对应服务：

- COS 标准存储
- 基础图片处理，可选

当前图片输入链路是：

```text
前端粘贴图片
├─ 转成 data:image/...;base64,...
├─ 写入 message_parts
└─ 如果模型支持图片，就直接传给 provider
```

这个方案适合快速验证，但生产上有几个问题：

- base64 很长，消息体膨胀
- 有些 provider 不支持 data URL
- 图片不方便长期保存、复用、预览和审计
- 大图片会增加前端、后端和模型请求压力

后续可以升级成：

```text
前端粘贴图片
├─ 上传到后端
├─ 后端保存到 COS
├─ 可选：基础图片处理生成缩略图 / 压缩版本
├─ 返回 image_url / thumbnail_url
├─ message_parts 保存 image_url
└─ 模型调用时传公网可访问或签名图片 URL
```

产品亮点可以写成：

- 支持图片附件持久化
- 支持图片预览、复用和审计
- 多模态输入不依赖超长 base64
- 支持后续图片压缩、缩略图和水印处理

技术价值：

- 大幅减少聊天消息体积
- 更容易兼容不支持 data URL 的模型供应商
- 图片可以长期挂在聊天记录、知识库引用或 Agent 操作记录里

优先级：

```text
高
```

---

### 2.3 文件预览缓存云端化

对应服务：

- COS 标准存储

当前 Office / PDF 预览可能会在本地生成缓存文件，例如：

```text
data/preview_cache/...
```

后续可以升级成：

```text
Office / 文档预览
├─ LibreOffice 或 ONLYOFFICE 生成 PDF / 预览文件
├─ 后端上传预览缓存到 COS
├─ MySQL 记录 preview_object_key
└─ 前端用签名 URL 打开预览
```

产品亮点可以写成：

- 高保真文档预览缓存
- 文档预览结果可复用，减少重复转换
- 预览文件和原始文件统一纳入云端资产管理

技术价值：

- 减少服务器磁盘压力
- 避免每次打开同一文档都重新转换
- 后续多实例部署时预览缓存不会散落在不同机器

优先级：

```text
中高
```

---

### 2.4 自动备份与迁移能力

对应服务：

- COS 标准存储

当前部署是单机 Docker，核心数据包括：

```text
MySQL
Redis
Chroma
data/user_docs
data/huggingface
data/sentence-transformers
```

后续可以做：

```text
定时备份
├─ MySQL dump
├─ Chroma 数据快照
├─ 用户文档目录
├─ 配置模板
└─ 上传到 COS backup/{date}/...
```

产品亮点可以写成：

- 支持文档和索引数据备份
- 支持服务器迁移和灾备恢复
- 支持按日期保留备份快照

技术价值：

- 降低单机磁盘损坏、误删、迁移失败的风险
- 后续换服务器时，先恢复对象存储和数据库即可

优先级：

```text
中
```

### 2.5 CDN 加速

对应服务：

- CDN 流量包

当前阶段不建议购买 CDN，因为：

- 用户量还不大
- 前端静态资源直接由 Nginx 返回即可
- 文档下载和预览流量还没有大到需要 CDN

后续如果系统访问量上来，可以接：

```text
CDN
├─ 前端静态资源加速
├─ 公共下载文件加速
├─ 图片缩略图加速
└─ 文档预览缓存加速
```

产品亮点可以写成：

- 静态资源和文档预览加速
- 大文件下载体验优化
- 图片附件访问加速

注意：

- 私有文档不能直接长期公开 CDN
- 需要配合签名 URL、防盗链、权限校验
- 先上 COS，再考虑 CDN，顺序更稳

优先级：

```text
低到中
```

### 2.6 HTTPS 与域名访问

对应服务：

- 域名：`kopai.work`
- SSL 证书
- Nginx 网关

这是当前上线阶段最重要的基础能力。

推荐域名规划：

```text
app.kopai.work       知识库主系统
office.kopai.work    ONLYOFFICE 文档服务
kopai.work           可作为官网或跳转入口
www.kopai.work       可作为官网或跳转入口
```

产品亮点可以写成：

- 独立品牌域名访问
- HTTPS 安全访问
- 前端、后端、ONLYOFFICE 统一由 Nginx 网关管理
- 外部访问 HTTPS，容器内部保留 HTTP，部署更清晰

优先级：

```text
最高
```

## 3. 不建议购买或暂不接入的服务

### 3.1 轻量对象存储

不建议现在买。

原因：

- 和 COS 标准存储定位重叠
- 10GB 容量偏小
- 外网流量通常也偏小
- 后续代码如果同时支持 COS 和轻量对象存储，会增加无必要复杂度

建议：

```text
统一走 COS 标准存储。
```

---

### 3.2 企业网盘

不建议现在买。

原因：

- 它是给人直接使用的独立网盘
- 当前系统已经有自己的文档库、文件夹、上传、预览、在线编辑、索引和检索
- 企业网盘不会自动进入 RAG 链路
- 只有 1 个月套餐，后续续费价值不高

除非后面明确要做：

```text
企业网盘文件同步到知识库
```

否则现在不需要。

## 4. 推荐落地阶段

### 第一阶段：域名 + HTTPS

目标：

```text
https://app.kopai.work
https://office.kopai.work
```

要做：

- DNS A 记录解析到服务器
- Nginx 接管公网 80 / 443
- 配置 SSL 证书
- `.env.prod` 改成域名地址
- ONLYOFFICE 文档服务也用 HTTPS 域名

价值：

- 正式可访问
- 避免 HTTPS 页面加载 HTTP ONLYOFFICE 被浏览器拦截
- 对外展示更专业

### 第一阶段补充：Let's Encrypt / certbot 自动续期操作步骤

这里推荐使用：

```text
宿主机 Nginx
+ Let's Encrypt 免费证书
+ certbot 自动续期
```

不要让 `kop-frontend` 容器继续直接占用公网 80。公网入口应该交给宿主机 Nginx：

```text
浏览器
├─ https://kopai.work
│  └─ 宿主机 Nginx -> http://127.0.0.1:18080 -> kop-frontend
├─ https://kopai.work/api/
│  └─ 宿主机 Nginx -> http://127.0.0.1:8000 -> kop-backend
└─ https://office.kopai.work
   └─ 宿主机 Nginx -> http://127.0.0.1:8088 -> middleware-onlyoffice
```

容器内部继续 HTTP：

```text
kop-backend -> http://middleware-onlyoffice
middleware-onlyoffice -> http://kop-backend:8000
```

#### 1. DNS 解析

在腾讯云 DNS 解析里确认至少有：

```text
kopai.work          A    42.193.201.53
www.kopai.work      A    42.193.201.53，可选
office.kopai.work   A    42.193.201.53
```

本地电脑验证：

```powershell
ping kopai.work
ping office.kopai.work
```

都应该解析到服务器公网 IP。

#### 2. 安全组放行

腾讯云安全组放行：

```text
80/tcp
443/tcp
```

如果后续 ONLYOFFICE 全部走 `https://office.kopai.work`，公网 `8088` 可以关闭或只绑定到本机。

#### 3. 改 `.env.prod`

服务器项目目录：

```bash
cd /opt/knowledge-orchestration-platform
cp .env.prod .env.prod.bak.$(date +%Y%m%d-%H%M%S)
nano .env.prod
```

建议改成：

```env
FRONTEND_HTTP_PORT=127.0.0.1:18080
BACKEND_HTTP_PORT=8000
VITE_API_BASE_URL=

CORS_ORIGINS=https://kopai.work,https://www.kopai.work

ONLYOFFICE_DOCUMENT_SERVER_URL=https://office.kopai.work
ONLYOFFICE_DOCUMENT_SERVER_INTERNAL_URL=http://middleware-onlyoffice
PUBLIC_BACKEND_URL=http://kop-backend:8000
PUBLIC_BACKEND_INTERNAL_URL=http://127.0.0.1:8000
```

重点：

- `ONLYOFFICE_DOCUMENT_SERVER_URL` 是浏览器访问地址，必须是 HTTPS。
- `ONLYOFFICE_DOCUMENT_SERVER_INTERNAL_URL` 是后端容器访问 ONLYOFFICE 的地址，继续 HTTP。
- `PUBLIC_BACKEND_URL` 是 ONLYOFFICE 容器下载文件和回调后端用的地址，继续 HTTP 内网地址。
- `VITE_API_BASE_URL=` 保持空，前端继续同源请求 `/api/...`。

#### 4. 重新创建前后端容器

因为端口映射和环境变量变了，需要重建容器，但不需要重新 build 镜像：

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --no-build --force-recreate backend frontend
docker compose --env-file .env.prod -f docker-compose.prod.yml ps
```

期望看到：

```text
kop-frontend   127.0.0.1:18080->80/tcp
kop-backend    127.0.0.1:8000->8000/tcp
```

如果前端仍然显示：

```text
0.0.0.0:80->80/tcp
```

说明 `FRONTEND_HTTP_PORT` 没改对，公网 80 还被前端容器占着，Nginx / certbot 后面会冲突。

#### 5. 检查 80 / 443 当前占用

服务器执行：

```bash
sudo ss -lntp | grep -E ':80|:443' || true
docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

目标状态：

```text
80/443 后续由宿主机 nginx 占用
kop-frontend 不直接占公网 80
kop-backend 只绑定 127.0.0.1:8000
```

#### 6. 安装 Nginx 和 certbot

```bash
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
```

启动 Nginx：

```bash
sudo systemctl enable nginx
sudo systemctl start nginx
```

要暂停（停止）本地的 Nginx，使用以下命令：

```bash
sudo systemctl stop nginx
```
#### 7. 先写 HTTP 版 Nginx 配置

先让 certbot 能通过 80 端口验证域名。

```bash
sudo nano /etc/nginx/conf.d/kopai.conf
```

写入：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80;
    server_name kopai.work www.kopai.work;

    client_max_body_size 100m;

    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }

    location / {
        proxy_pass http://127.0.0.1:18080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name office.kopai.work;

    client_max_body_size 2g;

    location / {
        proxy_pass http://127.0.0.1:8088;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }
}
```

检查并加载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

浏览器或命令验证 HTTP 临时可访问：

```bash
curl -I http://kopai.work
curl -I http://office.kopai.work/web-apps/apps/api/documents/api.js
```

#### 8. 申请 Let's Encrypt 证书

推荐用 `certonly --nginx`，让 certbot 只申请证书，不自动改你的 Nginx 配置：

```bash
sudo certbot certonly --nginx -d kopai.work -d www.kopai.work -d office.kopai.work
```

如果你不想启用 `www.kopai.work`，可以去掉：

```bash
sudo certbot certonly --nginx -d kopai.work -d office.kopai.work
```

成功后证书通常在：

```text
/etc/letsencrypt/live/kopai.work/fullchain.pem
/etc/letsencrypt/live/kopai.work/privkey.pem
```

注意：

- 即使证书包含 `office.kopai.work`，目录名也可能是第一个域名 `kopai.work`。
- `fullchain.pem` 是证书链。
- `privkey.pem` 是私钥，不能泄露。

#### 9. 改成 HTTPS 版 Nginx 配置

再次编辑：

```bash
sudo nano /etc/nginx/conf.d/kopai.conf
```

替换成：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80;
    server_name kopai.work www.kopai.work office.kopai.work;

    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name kopai.work www.kopai.work;

    ssl_certificate     /etc/letsencrypt/live/kopai.work/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/kopai.work/privkey.pem;

    client_max_body_size 100m;

    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_http_version 1.1;

        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }

    location / {
        proxy_pass http://127.0.0.1:18080;

}
```

#### 11. 配置自动续期后的 Nginx reload

certbot 安装后通常会自带 systemd timer 或 cron 自动续期。

检查：

```bash
systemctl list-timers | grep certbot || true
```

增加续期成功后的 Nginx reload hook：

```bash
sudo mkdir -p /etc/letsencrypt/renewal-hooks/deploy
sudo nano /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

写入：

```sh
#!/bin/sh
systemctl reload nginx
```

赋权：

```bash
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

测试自动续期流程：

```bash
sudo certbot renew --dry-run
```

如果 `dry-run` 成功，说明后续自动续期链路基本可用。

#### 13. 常见问题

如果申请证书失败，优先查：

```text
1. DNS 是否已经解析到当前服务器
2. 腾讯云安全组是否放行 80
```

## 7. HTTPS / Certbot 排障记录

本节记录 `kopai.work`、`www.kopai.work`、`office.kopai.work` 接入 HTTPS 时遇到的问题、判断过程和后续处理方案。

### 7.1 当前目标架构

最终目标是由宿主机 Nginx 统一接管公网入口：

```text
公网 80/443
└─ 宿主机 Nginx
   ├─ https://kopai.work / https://www.kopai.work -> 127.0.0.1:18080 前端容器
   ├─ https://kopai.work/api/                      -> 127.0.0.1:8000 后端容器
   └─ https://office.kopai.work                    -> 127.0.0.1:8088 ONLYOFFICE
```

容器侧保持内网或本机端口：

```text
kop-frontend  127.0.0.1:18080->80/tcp
kop-backend   127.0.0.1:8000->8000/tcp
ONLYOFFICE    0.0.0.0:8088->80/tcp
宿主机 nginx   0.0.0.0:80 / 0.0.0.0:443
```

这样做的原因：

- 证书、HTTPS、域名路由统一由宿主机 Nginx 管理。
- 前端容器自带的 Nginx 只负责提供静态页面，不直接占用公网 80/443。
- 后端和 ONLYOFFICE 可以继续使用 HTTP 内网访问，减少容器内部复杂度。

### 7.2 DNSPod 域名停靠导致证书验证失败

遇到的 certbot 报错：

```text
Certbot failed to authenticate some domains
Detail: 43.174.224.202: Invalid response from https://dnspod.qcloud.com/static/webblock.html?d=kopai.work
Detail: 43.174.225.201: Invalid response from https://dnspod.qcloud.com/static/webblock.html?d=www.kopai.work
Detail: 43.174.225.201: Invalid response from https://dnspod.qcloud.com/static/webblock.html?d=office.kopai.work
```

原因：

- DNSPod 的“域名停靠”功能会把域名指向 `domainparking-dnspod.cn.`。
- 该功能不是部署业务站点需要的功能，而是把域名指到 DNSPod 停靠页。
- Let’s Encrypt 验证域名时访问到了 DNSPod 停靠页，所以无法下载 challenge 文件。

正确 DNS 记录应为：

```text
主机记录    记录类型    线路类型    记录值
@           A           默认        42.193.201.53
www         A           默认        42.193.201.53
office      A           默认        42.193.201.53
```

不要保留这些记录：

```text
@       CNAME    domainparking-dnspod.cn.
www     CNAME    domainparking-dnspod.cn.
office  CNAME    domainparking-dnspod.cn.
```

也不要点击“域名停靠”里的“一键修复”，它会重新把记录改回停靠页。

### 7.3 DNS 正确但 certbot 仍访问停靠页

排查时已经确认权威 DNS 正确：

```bash
dig +short NS kopai.work
```

返回：

```text
cerdar.dnspod.net.
daniel.dnspod.net.
```

继续检查：

```bash
dig @cerdar.dnspod.net kopai.work A +short
dig @cerdar.dnspod.net www.kopai.work A +short
dig @cerdar.dnspod.net office.kopai.work A +short

dig @daniel.dnspod.net kopai.work A +short
dig @daniel.dnspod.net www.kopai.work A +short
dig @daniel.dnspod.net office.kopai.work A +short
```

结果均为：

```text
42.193.201.53
```

也检查过公共 DNS：

```bash
for d in kopai.work www.kopai.work office.kopai.work; do
  echo "===== $d ====="
  dig @cerdar.dnspod.net $d A +short
  dig @daniel.dnspod.net $d A +short
  dig @8.8.8.8 $d A +short
  dig @1.1.1.1 $d A +short
  dig @223.5.5.5 $d A +short
done
```

如果这些都返回 `42.193.201.53`，但 certbot 仍然报 `dnspod.qcloud.com/static/webblock.html`，说明不是本机 Nginx 或 Docker 的问题，而是 Let’s Encrypt 验证节点或部分公网递归 DNS 仍缓存了旧的 DNSPod 停靠页结果。

处理方式：

```text
1. 不要继续频繁运行正式 certbot，避免失败次数过多。
2. 等待 DNS 停靠页缓存过期，建议 30 到 60 分钟后再试。
3. 优先使用 --staging 测试，成功后再申请正式证书。
```

测试证书命令：

```bash
sudo certbot certonly --webroot -w /var/www/html --staging -d kopai.work -d www.kopai.work -d office.kopai.work
```

正式证书命令：

```bash
sudo certbot certonly --webroot -w /var/www/html -d kopai.work -d www.kopai.work -d office.kopai.work
```

### 7.4 Nginx 配置粘贴中断导致文件污染

遇到过的异常内容：

```text
EOF }   proxy_buffering off;600s;on $connection_upgrade;rwarded_for;
```

原因：

- 使用 `sudo tee /etc/nginx/conf.d/kopai.conf > /dev/null <<'EOF'` 粘贴大段配置时，中途按了 `Ctrl+C` 或粘贴不完整。
- Shell 没有正常读到最后独立一行 `EOF`，导致后续半截文本残留在配置文件或命令行中。

处理方式：

```bash
sudo truncate -s 0 /etc/nginx/conf.d/kopai.conf
sudo nano /etc/nginx/conf.d/kopai.conf
```

然后重新粘贴完整配置。保存后必须执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

只有看到下面结果才说明 Nginx 配置恢复正常：

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

### 7.5 证书不存在时不能提前启用 HTTPS 配置

```text
nginx: [emerg] cannot load certificate "/etc/letsencrypt/live/kopai.work/fullchain.pem"
BIO_new_file() failed
No such file or directory
```

原因：

- 证书还没有申请成功。
- Nginx 配置里已经写了：

```text
2. 通过 webroot 方式申请证书。
3. 确认 /etc/letsencrypt/live/kopai.work/fullchain.pem 存在。
4. 再切换到 HTTPS 最终配置。
```

检查证书文件：

```bash
sudo ls -la /etc/letsencrypt/live/kopai.work/
```

应该能看到：

```text
fullchain.pem
privkey.pem
cert.pem
chain.pem
```

### 7.6 申请证书前的临时 HTTP 配置

在证书还没有成功前，`/etc/nginx/conf.d/kopai.conf` 应使用 HTTP 临时配置，保证 certbot 可以访问 `/.well-known/acme-challenge/`。

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80;
    listen [::]:80;
    server_name kopai.work www.kopai.work;

    client_max_body_size 200m;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }

    location / {
        proxy_pass http://127.0.0.1:18080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    listen [::]:80;
    server_name office.kopai.work;

    client_max_body_size 2g;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        proxy_pass http://127.0.0.1:8088;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }
}
```

```bash
sudo mkdir -p /var/www/html/.well-known/acme-challenge
```

### 7.9 当前判断

截至本次排障，Nginx 配置已经能通过：

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

但 certbot `--nginx` 和 `--webroot` 都仍然访问到 DNSPod 停靠页：

```text
https://dnspod.qcloud.com/static/webblock.html
```

因此当前最可能原因是：

```text
DNSPod 停靠记录已经删除，权威 DNS 和常见公共 DNS 已经返回 42.193.201.53；
但 Let’s Encrypt 验证节点或某些公网递归 DNS 仍缓存旧的停靠页解析。
```

```text
1. 保持当前 HTTP 临时 Nginx 配置，不要提前切 HTTPS。
2. 等待 30 到 60 分钟。
3. 先跑 --staging 测试证书。

5. 正式证书成功后再切换 HTTPS 最终配置。
```

如果等待较久仍不成功，可以考虑临时使用 DNS TXT 验证方式：

```bash
sudo certbot certonly --manual --preferred-challenges dns --staging -d kopai.work -d www.kopai.work -d office.kopai.work
```

但手动 DNS 验证默认不利于自动续期；长期方案仍建议使用 HTTP/webroot 验证，或者后续接入 DNSPod API 自动 DNS 验证。
