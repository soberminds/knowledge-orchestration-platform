# 文档库文件夹化与用户关联设计

这份文档专门记录“文档上传与文档管理页面”的下一步优化方向。

当前文档页面已经从“后端扫描文件路径的列表”切换到“DB 文档库 + 用户文件夹”的新方案。

当前已经确定的方向是：

- 文档必须关联用户
- 用户可以创建自己的文件夹
- 上传时可以选择目标文件夹
- 页面默认展示文件夹图标和文件列表
- 点击文件夹进入下一层
- 打开文件时看到的是用户理解的路径，而不是后端磁盘路径
- 索引、检索、权限都围绕用户和文件夹做隔离

---

## 1. 当前页面为什么看起来别扭

之前文档页展示的是后端返回的 `DocumentInfo[]`，并且混合了旧的磁盘扫描目录。

代码位置：

- `frontend/src/components/workspaces/DocumentsWorkspace.vue`
- `app/api/routes.py`
- `app/services/knowledge_base.py`
- `app/services/files.py`

当前后端接口：

```text
GET /api/documents
```

旧后端做法大概是：

```text
扫描旧的本地样例目录
扫描旧的上传目录
把所有支持的文件平铺返回给前端
```

所以旧界面里前端看到的是：

```text
旧本地样例目录/xxx.md
旧上传目录/xxx.docx
```

这个对开发者来说能看懂，但对普通用户来说有几个问题：

- 路径太技术化
- 文件夹层级没有视觉表达
- 用户不知道文件属于谁
- 上传时不能选择放在哪个文件夹
- 文件列表越多越难管理
- 后续多用户时会有权限和数据隔离问题

现在已经收口为：

```text
GET /api/documents
└─ 只查询 DocumentLibraryService
   ├─ kop_doc_folder
   └─ kop_doc_file
```

也就是说，旧本地样例目录、旧上传目录、样例文档目录都不再作为正式文档库来源。

## 3. 用户关联应该怎么做

是的，文档库应该关联用户。

当前项目已经有聊天记忆相关的用户表：

```text
kop_user
```

现在本地开发阶段使用的是默认用户，例如：

```text
local-user
```

所以文档库也应该复用这个用户体系。

当前阶段可以这样理解：

```text
没有登录系统
└─ 后端自动使用默认本地用户 local-user
   ├─ 聊天记录属于 local-user
   ├─ 文档文件夹属于 local-user
   └─ 上传文件也属于 local-user
```

后续真正登录后：

```text
用户登录
└─ 后端从 token / session 里拿 user_id
   ├─ 只返回这个用户自己的文件夹
   ├─ 只返回这个用户自己的文件
   ├─ 检索时只检索这个用户有权限的 chunk
   └─ 删除、编辑、下载都要校验 user_id
```

不要让前端直接传 `user_id` 决定归属。

更安全的做法是：

```text
前端请求
└─ 后端根据当前登录态识别用户
   └─ 得到 current_user_id
      └─ 所有文件夹和文件操作都自动带上 current_user_id
```

本地阶段还没有登录时，就用：

```text
current_user_id = 默认本地用户 id
```

## 4. 不建议直接让用户输入真实磁盘路径

用户可以自定义“文件夹”，但这里的文件夹应该是“应用内文件夹”，不是让用户输入任意磁盘路径。

不要这样设计：

```text
用户输入：E:\某个目录\资料
后端直接往这个目录写文件
```

原因：

- 路径安全风险很高
- Docker 部署后宿主机路径和容器路径不一致
- 多用户权限很难控制
- 删除、移动、索引都容易出错

推荐这样设计：

```text
用户看到：
我的文档 / 项目资料 / 合同

数据库保存：
folder_id = 15
parent_id = 3
user_id = 1
name = 合同

后端真实存储：
data/user_docs/1/15/xxx.docx
```

也就是说：

- 用户看到的是“业务路径”
- 后端保存的是“受控路径”
- 数据库负责关联两者
- 后端永远不信任前端传来的磁盘路径

## 5. 推荐数据模型

可以新增两张核心表：

1. `kop_doc_folder`
2. `kop_doc_file`

后续如果要做版本管理，再加：

3. `kop_doc_file_version`

### 5.1 文件夹表 `kop_doc_folder`

用途：

- 保存用户创建的文件夹
- 支持父子层级
- 支持文件夹树

建议字段：

```text
id
user_id
parent_id
name
path_cache
sort_order
status
created_at
updated_at
```

字段说明：

- `id`：文件夹 id
- `user_id`：属于哪个用户
- `parent_id`：父文件夹 id，根目录可以为空
- `name`：文件夹名称
- `path_cache`：冗余保存展示路径，例如 `/项目资料/合同`
- `sort_order`：排序
- `status`：状态，正常 / 删除

树状关系：

```text
kop_user
└─ kop_doc_folder
   ├─ 我的文档
   │  ├─ 项目资料
   │  │  └─ 合同
   │  └─ 会议纪要
   └─ 测试样例
```

### 5.2 文件表 `kop_doc_file`

用途：

- 保存文件元数据
- 记录文件属于哪个用户、哪个文件夹
- 记录真实存储路径
- 记录索引状态

建议字段：

```text
id
user_id
folder_id
display_name
original_name
stored_name
storage_path
extension
mime_type
size_bytes
sha256
index_status
index_message
status
created_at
updated_at
```

字段说明：

- `id`：文件 id，后续前端打开文件最好用这个
- `user_id`：文件属于哪个用户
- `folder_id`：文件在哪个文件夹
- `display_name`：界面展示名称
- `original_name`：用户上传时的原始文件名
- `stored_name`：后端为了避免重名生成的真实文件名
- `storage_path`：后端受控存储路径
- `extension`：扩展名，例如 `.docx`
- `mime_type`：文件类型
- `size_bytes`：文件大小
- `sha256`：文件内容 hash，用于去重、变更检测
- `index_status`：索引状态，例如 `pending / indexing / success / failed`
- `index_message`：索引错误或成功信息
- `status`：正常 / 删除

关系：

```text
kop_user
└─ kop_doc_folder
   └─ kop_doc_file
```

一个用户可以有多个文件夹。

一个文件夹可以有多个文件。

一个文件只属于一个文件夹。

## 6. 推荐 SQL 草案

可以在后续建表脚本中加入类似下面的结构。

```sql
CREATE TABLE IF NOT EXISTS `kop_doc_folder` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id` bigint unsigned NOT NULL COMMENT '所属用户',
  `parent_id` bigint unsigned DEFAULT NULL COMMENT '父文件夹 id，根目录为空',
  `name` varchar(128) NOT NULL COMMENT '文件夹名称',
  `path_cache` varchar(1024) NOT NULL DEFAULT '' COMMENT '展示路径缓存，例如 /项目资料/合同',
  `sort_order` int NOT NULL DEFAULT 0 COMMENT '排序',
  `status` tinyint NOT NULL DEFAULT 1 COMMENT '状态：1 正常，0 删除',
  `created_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `updated_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_kop_doc_folder_user_parent` (`user_id`, `parent_id`, `status`),
  KEY `idx_kop_doc_folder_parent` (`parent_id`),
  CONSTRAINT `fk_kop_doc_folder_user`
    FOREIGN KEY (`user_id`) REFERENCES `kop_user` (`id`)
    ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT `fk_kop_doc_folder_parent`
    FOREIGN KEY (`parent_id`) REFERENCES `kop_doc_folder` (`id`)
    ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='KOP 文档文件夹表';
```

```sql
CREATE TABLE IF NOT EXISTS `kop_doc_file` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id` bigint unsigned NOT NULL COMMENT '所属用户',
  `folder_id` bigint unsigned DEFAULT NULL COMMENT '所属文件夹 id，根目录文件为空',
  `display_name` varchar(255) NOT NULL COMMENT '界面展示文件名',
  `original_name` varchar(255) NOT NULL COMMENT '上传原始文件名',
  `stored_name` varchar(255) NOT NULL COMMENT '后端实际存储文件名',
  `storage_path` varchar(1024) NOT NULL COMMENT '后端受控存储相对路径',
  `extension` varchar(32) NOT NULL DEFAULT '' COMMENT '扩展名',
  `mime_type` varchar(128) DEFAULT NULL COMMENT 'MIME 类型',
  `size_bytes` bigint unsigned NOT NULL DEFAULT 0 COMMENT '文件大小',
  `sha256` char(64) DEFAULT NULL COMMENT '内容 hash',
  `index_status` varchar(32) NOT NULL DEFAULT 'pending' COMMENT '索引状态：pending/indexing/success/failed',
  `index_message` text DEFAULT NULL COMMENT '索引状态说明',
  `status` tinyint NOT NULL DEFAULT 1 COMMENT '状态：1 正常，0 删除',
  `created_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `updated_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_kop_doc_file_user_folder` (`user_id`, `folder_id`, `status`, `updated_at`),
  KEY `idx_kop_doc_file_user_name` (`user_id`, `display_name`),
  KEY `idx_kop_doc_file_index_status` (`index_status`),
  CONSTRAINT `fk_kop_doc_file_user`
    FOREIGN KEY (`user_id`) REFERENCES `kop_user` (`id`)
    ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT `fk_kop_doc_file_folder`
    FOREIGN KEY (`folder_id`) REFERENCES `kop_doc_folder` (`id`)
    ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='KOP 文档文件表';
```

## 7. 后端接口应该怎么改

当前接口偏路径驱动：

```text
GET    /api/documents
POST   /api/upload
GET    /api/file?path=...
DELETE /api/documents?path=...
```

后续建议升级成“文件夹 + 文件 id”驱动。

### 7.1 文件夹接口

```text
GET    /api/doc-folders/tree
GET    /api/doc-folders/children?parent_id=...
POST   /api/doc-folders
PATCH  /api/doc-folders/{folder_id}
DELETE /api/doc-folders/{folder_id}
```

用途：

- 加载文件夹树
- 点击文件夹时加载子文件夹
- 新建文件夹
- 重命名文件夹
- 删除文件夹

### 7.2 文件浏览接口

```text
GET /api/documents/browse?folder_id=...&page=1&page_size=50&keyword=...
```

返回：

```text
当前文件夹信息
子文件夹列表
文件列表
分页信息
面包屑路径
```

返回结构可以像这样：

```json
{
  "folder": {
    "id": 15,
    "name": "合同",
    "parent_id": 3
  },
  "breadcrumbs": [
    { "id": null, "name": "我的文档" },
    { "id": 3, "name": "项目资料" },
    { "id": 15, "name": "合同" }
  ],
  "folders": [
    { "id": 21, "name": "2026", "updated_at": "..." }
  ],
  "files": [
    {
      "id": 1001,
      "display_name": "healthcheck.docx",
      "extension": ".docx",
      "size_bytes": 12345,
      "index_status": "success",
      "updated_at": "..."
    }
  ],
  "page": 1,
  "page_size": 50,
  "has_more": false
}
```

### 7.3 上传接口

```text
POST /api/documents/upload
```

表单字段：

```text
folder_id
files[]
```

逻辑：

```text
识别 current_user_id
校验 folder_id 属于 current_user_id
保存文件到受控目录
写入 kop_doc_file
触发单文件索引
返回上传结果
```

### 7.4 文件操作接口

```text
GET    /api/documents/{file_id}/file
GET    /api/documents/{file_id}/page-text
GET    /api/documents/{file_id}/preview-pdf
GET    /api/documents/{file_id}/office-config
PUT    /api/documents/{file_id}/edit-text
PATCH  /api/documents/{file_id}/rename
PATCH  /api/documents/{file_id}/move
POST   /api/documents/{file_id}/reindex
DELETE /api/documents/{file_id}
```

这样前端不再需要到处传：

```text
后端磁盘路径/xxx.docx
```

而是传：

```text
file_id = 1001
```

后端根据 `file_id` 查数据库，再校验：

```text
file.user_id == current_user_id
```

通过以后才允许查看、编辑、删除。

## 8. 文件真实存储路径怎么安排

推荐受控存储目录：

```text
data/user_docs/{user_id}/{folder_id}/{file_id}_{safe_filename}
```

例子：

```text
data/user_docs/1/15/1001_healthcheck.docx
```

用户看到的是：

```text
我的文档 / 项目资料 / 合同 / healthcheck.docx
```

后端实际使用的是：

```text
data/user_docs/1/15/1001_healthcheck.docx
```

这样做的好处：

- 用户路径更好看
- 后端路径更安全
- 不怕重名
- 多用户隔离清楚
- Docker 部署路径稳定
- 后续迁移对象存储也更容易

## 9. 和 Chroma 索引怎么关联

现在 Chroma 里主要靠 `source` 路径关联文件。

后续建议每个 chunk 的 metadata 里增加这些字段：

```text
user_id
file_id
folder_id
display_name
folder_path
source
page
sheet
slide
chunk_index
char_count
```

一个文件进入索引后的关系应该是：

```text
kop_doc_file
└─ 原始文件
   ├─ 解析成多个 Document
   ├─ 切成多个 chunk
   ├─ 每个 chunk 生成一个向量
   └─ 写入 Chroma
      ├─ vector
      ├─ chunk 原文
      └─ metadata
         ├─ user_id
         ├─ file_id
         ├─ folder_id
         └─ chunk_index
```

检索时必须带用户过滤：

```text
用户提问
├─ 得到 current_user_id
├─ 问题向量化
├─ Chroma 检索
│  └─ where: user_id = current_user_id
├─ 如果当前会话绑定了某个文件夹
│  └─ 再 where: folder_id in 可检索范围
└─ 返回该用户有权限的 chunk
```

这样可以避免：

```text
A 用户上传的文件被 B 用户检索到
```

### 9.1 移动文件夹要不要重新索引

有两种做法。

#### 做法 A：移动后重新索引

简单粗暴：

```text
文件移动到新文件夹
├─ 更新数据库 folder_id
├─ 删除旧 Chroma chunk
└─ 重新索引这个文件
```

优点：

- 实现简单
- metadata 一定最新

缺点：

- 移动大量文件时慢

#### 做法 B：用 file_id 做稳定关联

更推荐长期做法：

```text
Chroma metadata 里稳定保存 file_id
文件夹路径显示时从 MySQL 查
```

这样文件移动时：

```text
只更新 MySQL 的 folder_id
不需要重新向量化
```

因为文件内容没有变，向量也不用重新生成。

当前项目可以先用做法 A，后面再优化成做法 B。

## 11. 推荐分阶段实现

### 第一阶段：先把界面变成文件夹体验

目标：

- 前端不再平铺全部路径
- 可以按目录层级展示
- 上传默认进入当前目录

这个阶段原本可以用磁盘目录快速过渡，但现在已经跳过这条临时路线，直接进入 DB 文档库方案。

旧的本地样例目录和旧上传目录扫描方式已经不再作为正式入口。

### 第二阶段：加入数据库文件夹和文件表

目标：

- `kop_doc_folder`
- `kop_doc_file`
- 上传文件写 DB
- 文件列表从 DB 查询
- 文件操作从 `path` 改成 `file_id`

这一阶段完成后，文档库才真正像业务系统。

当前已落地的第二阶段内容：

- 新增 `app/services/document_library.py`，由它统一管理 `kop_doc_folder` 和 `kop_doc_file`
- 后端继续使用默认本地用户 `local-user`，文档文件夹和上传文件都会归属到这个用户
- 新上传到 DB 文档库的文件，真实存储在 `data/user_docs/{user_id}/{folder_id 或 root}`
- `GET /api/documents` 只返回 DB 文档库数据，前端用 `display_path` 展示成用户理解的文件夹路径
- `data/user_docs` 的真实物理路径不会直接暴露成前端文件夹树，而是通过 DB 里的 `display_path` 展示
- 打开、预览、文本编辑、ONLYOFFICE 编辑已经允许访问 `data/user_docs`
- 上传和新建文件夹只使用 `parent_id / folder_id`
- 删除文件只走 DB 文档库删除，并同步删除 `data/user_docs` 下的真实文件
- 旧的本地样例目录、旧上传目录、样例文档目录已经不再作为文档库入口

这一阶段还没有完全做完的部分：

- 文件操作接口还保留 `path` 参数，没有彻底改成 `file_id`
- Chroma 里的 chunk metadata 还没有正式写入 `user_id / file_id / folder_id`
- 还没有做移动、重命名、文件夹删除、文件夹权限校验
- 前端上传弹窗还没有做“手动选择目标文件夹”，目前是默认上传到当前打开的文件夹
- 删除 DB 文件后会重建索引，但还不是按 `file_id` 精准删除对应 chunk

所以现在可以理解为：

```text
第二阶段已经完成了“DB 文档库主链路”
但还没有完成“文件 id 化、权限化、索引 metadata 化”
```

### 第三阶段：索引 metadata 加 user_id / file_id / folder_id

目标：

- Chroma chunk 和数据库文件记录关联
- 检索时按用户过滤
- 删除文件时能删除该文件所有 chunk
- 文件移动、重命名后引用更稳定

### 第四阶段：多用户、工作区、知识库绑定

目标：

- 用户可以有多个知识库空间
- 会话可以绑定某个知识库或文件夹
- 权限控制更细

可以扩展成：

```text
workspace
└─ folder
   └─ file
      └─ chunks
```

## 12. 推荐最终业务流程

### 12.1 上传文件

```text
用户选择文件
├─ 选择目标文件夹
├─ 前端提交 folder_id + files
├─ 后端识别 current_user_id
├─ 校验 folder_id 属于 current_user_id
├─ 保存文件到 data/user_docs/{user_id}/{folder_id}/
├─ 写入 kop_doc_file
├─ 文件解析
├─ 切片
├─ embedding
├─ 写入 Chroma
└─ 更新 kop_doc_file.index_status
```

### 12.2 查看文件夹

```text
用户点击文件夹
├─ 前端请求 /api/documents/browse?folder_id=...
├─ 后端识别 current_user_id
├─ 查询该用户该文件夹下的子文件夹
├─ 查询该用户该文件夹下的文件
└─ 返回 folders + files + breadcrumbs
```

### 12.3 查看文件

```text
用户点击文件
├─ 前端传 file_id
├─ 后端查 kop_doc_file
├─ 校验 user_id
├─ 找到 storage_path
└─ 根据文件类型进入对应查看器
```

### 12.4 检索问答

```text
用户提问
├─ 后端识别 current_user_id
├─ 问题向量化
├─ Chroma 检索
│  └─ 过滤 user_id
├─ 拿到 chunk
├─ 根据 file_id 补文件显示名和路径
└─ 组织上下文给 LLM
```

## 13. 这件事和当前代码的关系

当前代码：

```text
DocumentsWorkspace.vue
└─ documents: DocumentInfo[]
   └─ 直接渲染 doc.path
```

后续建议：

```text
DocumentsWorkspace.vue
├─ currentFolder
├─ breadcrumbs
├─ folders
└─ files
```

当前后端：

```text
DocumentLibraryService.list_documents()
└─ 查询 kop_doc_folder 和 kop_doc_file
```

后续建议：

```text
DocumentLibraryService
├─ list_folder_children(user_id, folder_id)
├─ upload_files(user_id, folder_id, files)
├─ create_folder(user_id, parent_id, name)
├─ move_file(user_id, file_id, target_folder_id)
├─ rename_file(user_id, file_id, new_name)
└─ delete_file(user_id, file_id)
```

当前知识库索引：

```text
source path -> Document -> chunk -> Chroma
```

后续建议：

```text
kop_doc_file.id
└─ storage_path
   └─ Document
      └─ chunk
         └─ Chroma metadata: user_id / file_id / folder_id
```

## 14. 一句话总结

文档库不应该继续展示成一串后端磁盘技术路径。

更合理的是：

```text
用户
└─ 我的文档
   ├─ 文件夹
   │  └─ 文件
   └─ 文件夹
      └─ 文件
```

底层再映射到：

```text
MySQL 负责用户、文件夹、文件元数据
本地磁盘负责真实文件内容
Chroma 负责文件切片后的向量索引
Redis 可选负责热缓存
```

这样页面会更像文件系统，权限也更清晰，后续多用户、多知识库、Docker 部署都会更容易继续往下做。
