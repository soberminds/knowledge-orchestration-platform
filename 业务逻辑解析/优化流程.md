第一阶段
MySQL：存会话、消息、摘要

# 优化流程

这份文档专门记录当前项目在“上下文长度、聊天记忆、会话存储、数据库设计”上的优化思路。

它不是一份空泛的理论笔记，而是尽量贴着当前项目代码和后续可落地的实现来写。

---

## 1. 为什么要做这类优化

RAG 和聊天系统真正落地时，最常见的问题不是“模型不会回答”，而是：

- 上下文越来越长，prompt 很快就超了
- 历史消息越堆越多，回答会变慢、变贵
- 老问题和老偏好容易丢
- 检索到的知识库内容很准，但聊天连续性不够
- 只靠前端传 history，无法做稳定的长期记忆

所以要做的不是“无限加长上下文”，而是把记忆分层。

---

## 2. 当前项目的现状

当前项目里，聊天相关逻辑主要集中在 `app/services/knowledge_base.py`。

现在的行为大致是：

- `_compose_search_query(question, history)` 只取最近 6 条历史消息，用来改写检索问题
- `_prepare_answer(...)` 会把 `history` 拼到最终提示词里
- `_build_context(...)` 会把检索命中的 chunk 做分组、裁剪和引用整理
- 最终再把“问题 + 历史 + 检索上下文 + 证据标签”一起发给模型

这说明：

- 检索阶段已经有“最近历史窗口”
- 但回答阶段的 history 还是偏“直接拼接”
- 如果前端传进来的历史很长，prompt 仍然会膨胀

所以后续最好引入“摘要 + 最近窗口 + 长期记忆”的分层机制。

---

## 3. 推荐的上下文分层

推荐把模型真正看到的上下文拆成下面几层：

```text
模型真正看到的上下文
├─ 系统提示词
├─ 当前会话摘要
├─ 最近几轮对话
├─ 知识库检索结果
├─ 外部网页检索结果（可选）
└─ 当前问题
```

对应职责如下：

### 3.1 系统提示词

负责告诉模型：

- 你是谁
- 说话风格
- 是否优先使用知识库证据
- 是否允许使用常识补充
- 是否要保留引用标签

### 3.2 会话摘要

负责压缩很早以前的聊天内容。

它的作用不是完整复原对话，而是保留“对当前会话仍然有用的状态”：

- 当前用户在做什么项目
- 已经讨论过哪些方案
- 哪些结论已经达成
- 用户偏好是什么

### 3.3 最近几轮对话

保留最近 4 到 8 轮消息通常最实用。

这部分最贴近当前问题，模型最容易接住上下文。

### 3.4 知识库检索结果

这是 RAG 的核心证据层。

它不是聊天历史，而是：

- 文件切片
- 向量检索命中的 chunk
- 经过裁剪、分组、引用整理后的上下文块

### 3.5 当前问题

用户当前这一轮到底在问什么，始终是第一优先级。

---

## 4. 推荐的记忆结构

建议把记忆拆成四层，不要混在一起。

### 4.1 原始聊天记录

用途：

- 记录完整问答
- 方便回放
- 方便排查问题
- 方便审计

特点：

- 量最大
- 不适合直接塞进 prompt

### 4.2 会话摘要

用途：

- 压缩长期聊天
- 让 prompt 保持稳定
- 给模型提供连续背景

特点：

- 内容更短
- 会随着对话增长而更新
- 比原始消息更适合进 prompt

### 4.3 最近窗口

用途：

- 保留最近几轮对话
- 保持当前回答的连贯性

特点：

- 只放少量消息
- 每次请求动态生成

### 4.4 长期记忆

用途：

- 记录用户稳定偏好
- 记录长期项目状态
- 记录可以跨会话复用的事实

特点：

- 不是所有消息都该进长期记忆
- 只存“稳定、可复用、对后续有帮助”的内容

---

## 5. 推荐数据库设计

如果后面要做正式的多人系统，我建议主存储用 MySQL。

Redis 可以做短期缓存，但不建议当唯一存储。

### 5.1 用户表 `app_user`

用途：

- 用户身份管理
- 后续聊天会话关联用户

建议字段：

- `id`
- `username`
- `password_hash`
- `nickname`
- `status`
- `created_at`
- `updated_at`

### 5.2 会话表 `chat_conversation`

用途：

- 一次聊天对应一条会话记录
- 作为消息表的父表

建议字段：

- `id`
- `user_id`
- `title`
- `model`
- `workspace_id` 或 `kb_id`
- `summary`
- `last_message_at`
- `is_deleted`
- `created_at`
- `updated_at`

### 5.3 消息表 `chat_message`

用途：

- 保存每一条用户消息、助手消息、系统消息

建议字段：

- `id`
- `conversation_id`
- `sender_user_id`
- `role`，例如 `user / assistant / system / tool`
- `content`
- `seq_no`
- `meta_json`
- `citations_json`
- `token_count`
- `created_at`

建议索引：

- `(conversation_id, seq_no)`
- `(conversation_id, created_at)`
- `(sender_user_id, created_at)`

### 5.4 会话摘要表 `chat_conversation_summary`

用途：

- 保存压缩后的历史摘要
- 让老对话不必一直塞进 prompt

建议字段：

- `id`
- `conversation_id`
- `summary_text`
- `covered_to_message_id`
- `version`
- `created_at`
- `updated_at`

### 5.5 长期记忆表 `chat_memory_fact`

用途：

- 保存稳定事实
- 给后续会话复用

建议字段：

- `id`
- `user_id`
- `fact_text`
- `confidence`
- `source_message_id`
- `embedding_ref`
- `created_at`

适合存的内容例子：

- 用户偏好中文回答
- 用户常用 Docker 中间件
- 用户项目路径固定
- 用户更喜欢树状图或流程图式说明

### 5.6 可选关系表 `conversation_kb_bind`

如果后面一个会话要绑定多个知识库，可以再加这张关系表。

建议字段：

- `id`
- `conversation_id`
- `kb_id`
- `created_at`

---

## 6. Redis 适合放什么

Redis 更适合做“短期、热数据、临时状态”：

- 最近几轮消息缓存
- 当前会话摘要缓存
- 流式生成中的中间状态
- 限流计数
- 临时锁

不建议：

- 把 Redis 当唯一聊天库
- 把所有历史都只放 Redis

聊天记录最终还是要落 MySQL，这样更稳。

---

## 7. 推荐的请求流程

推荐把一次问答流程设计成下面这样：

```text
用户提问
├─ 从 MySQL 读取会话摘要
├─ 从 MySQL 读取最近 N 条消息
├─ 组装 prompt
│  ├─ 系统提示词
│  ├─ 会话摘要
│  ├─ 最近对话
│  ├─ 当前问题
│  └─ 知识库检索结果
├─ 先做检索问题改写
├─ 再去 Chroma 检索知识库
├─ 把检索结果整理成上下文
├─ 调用大模型生成回答
├─ 把用户消息写入 chat_message
├─ 把助手回复写入 chat_message
└─ 必要时更新会话摘要
```

这个流程的好处是：

- 上下文不会无限变长
- 会话可以长期维持
- 聊天记录可以完整保存
- 知识库证据和聊天记忆不会互相污染

## 8. 分阶段推进建议

### 第一阶段：先把“能稳定保存和读取”做起来

目标：

- 先把消息存库
- 先把会话和用户关联起来
- 先只使用“最近窗口 + 简单历史摘要”

这一阶段重点不是记忆很聪明，而是结构稳定。

建议实现：

- MySQL 建表
- 保存用户、会话、消息
- 前端传历史不再是唯一来源
- 后端从数据库回读最近消息

### 第二阶段：加入摘要压缩

目标：

- 让长会话不爆 prompt
- 把老消息压成摘要

建议实现：

- 对每个会话保存摘要
- 当消息数量或 token 超过阈值时触发总结
- 只把“摘要 + 最近窗口”拼进 prompt

建议阈值思路：

- 消息数超过 12 条后开始摘要
- 或者估算 token 超过某个阈值后摘要

### 第三阶段：加入长期记忆

目标：

- 记住用户稳定偏好
- 记住项目长期状态

建议实现：

- 提取稳定事实
- 存入长期记忆表
- 必要时做 embedding 检索

这一步能让系统更像“真的记得你”，但要控制好筛选条件，不要什么都记。

### 第四阶段：支持多用户、多工作区、多知识库

目标：

- 一套系统服务多个用户
- 一套会话能绑定多个知识库
- 后续权限控制更清晰

建议实现：

- 增加 `tenant_id` 或 `workspace_id`
- 所有聊天、摘要、记忆、知识库绑定都带归属

---

## 9. 什么不建议一开始就做

先别急着上这些：

- 一上来就把所有聊天都做向量化
- 一上来就把所有历史都塞进 prompt
- 一上来就做很复杂的“全局记忆系统”
- 一上来就把 Redis 当主库

原因很简单：

- 复杂度会突然飙高
- 排查问题会很痛苦
- 记忆越多，不一定越好，反而可能污染回答

---

## 10. 跟当前项目的结合点

当前项目已经有：

- RAG 检索链路
- Chroma 向量库
- 文件解析
- 文档切片
- 模型调用

后续要补的是：

- 聊天记录持久化
- 会话摘要
- 最近窗口读取
- 用户关联
- 长期记忆

也就是说，RAG 负责“知识”，聊天库负责“对话状态”。

这两条线最好分开，不要混成一个表。

---

## 11. 一句话总结

最实用的做法是：

- 原始消息进 MySQL
- 最近窗口进 prompt
- 老消息压成摘要
- 长期稳定信息单独存
- Redis 负责热缓存
- Chroma 负责知识库检索

这样系统会比“把所有历史都拼进去”稳定得多，也更适合后面扩展到云端部署和多用户场景。

## 12. 当前已经落地的第一阶段实现

本次已经先把“聊天记录能稳定保存和读取”这一步接起来了。

### 12.1 新增后端模块

```text
app/core/database.py
├─ 负责拼 MySQL 连接地址
├─ 负责创建 SQLAlchemy engine
└─ 提供 session_scope() 统一管理事务

app/core/redis_client.py
├─ 负责创建 Redis 客户端
└─ 用于缓存最近聊天窗口

app/services/chat_memory.py
├─ 自动创建/读取本地默认用户
├─ 自动创建/读取会话
├─ 从 Redis 或 MySQL 读取最近消息
├─ 保存用户消息和助手消息
└─ 保存后刷新 Redis 最近消息缓存
```

### 12.2 当前请求链路

```text
前端发送问题
├─ 如果当前前端会话已有 backendConversationId
│  └─ 请求里带 conversation_id
├─ 如果没有
│  └─ 后端自动创建新会话
├─ 后端从 MySQL/Redis 读取最近消息窗口
├─ 把最近窗口交给原来的 RAG 问答链路
├─ 大模型生成回答
├─ 后端把本轮 user / assistant 两条消息写入 MySQL
├─ 后端刷新 Redis 最近消息缓存
└─ 后端把 conversation_id 返回给前端
```

### 12.3 前端当前做了什么

前端的 `ChatSession` 新增了：

- `backendConversationId`

它的作用是把“前端临时会话”和“后端数据库会话”关联起来。

第一次提问时：

- 前端没有 `backendConversationId`
- 后端创建会话
- 后端返回 `conversation_id`
- 前端保存到当前 `ChatSession.backendConversationId`

后续同一个会话继续提问时：

- 前端带上 `conversation_id`
- 后端就能回读这条会话的最近消息

### 12.4 当前已经使用的表

当前代码已经直接使用：

- `kop_user`
- `kop_chat_conversation`
- `kop_chat_message`

当前已经预留但还没有正式启用：

- `kop_chat_conversation_summary`
- `kop_chat_memory_fact`

### 12.5 当前配置入口

配置已经写入：

- `.env`
- `.env.example`

主要配置包括：

- `MYSQL_HOST`
- `MYSQL_PORT`
- `MYSQL_DATABASE`
- `MYSQL_USER`
- `MYSQL_PASSWORD`
- `REDIS_HOST`

- `CHAT_CACHE_TTL_SEC`

建表脚本位置：

- `业务逻辑解析/KOP聊天记忆建表.sql`

### 12.6 现在还没有做的事情

第一阶段先不做这些：

- 自动会话摘要生成
- 长期记忆事实抽取
- 聊天历史向量化
- 多用户登录认证
- 会话列表接口
- 删除/重命名会话接口

这些更适合等“消息能稳定入库、回读、前端关联会话”跑通以后，再分阶段加。
