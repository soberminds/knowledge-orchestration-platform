### 问题 1：以后本地部署模型，是否还能兼容 OpenAI 风格调用？

结论：**只要本地模型服务暴露 OpenAI 兼容接口，就可以继续兼容；如果本地模型只有自己的原生接口，就需要新增 provider adapter。**

第一阶段重构后，当前系统的模型调用核心已经拆成两层：

- `app/services/knowledge_base.py`：负责 RAG 编排、检索、prompt 组织、回答归一化
- `app/services/llm_provider_adapter.py`：负责 provider 调用、OpenAI-compatible client 缓存、参数降级重试

目前落地的 adapter 是 `OpenAICompatibleProviderAdapter`，它内部仍然通过：

```python
from openai import OpenAI

client = OpenAI(api_key=..., base_url=...)
client.chat.completions.create(...)
```

## 近期模型能力 Bug 修复记录

### 1. 思考片段展示一字一行、换行溢出

表现：

- 助手消息下面的“思考片段”展开后，内容像截图那样一字一行。
- 容器被撑高，阅读体验很差。

原因：

- 流式接口返回的 `reasoning_delta` 本来就是很多小片段。
- 前端原来把每一个 delta 都当成一个独立 `<p>` 渲染。
- 如果模型按字、短词或很短的 token 返回思考内容，就会变成很多段落。

涉及文件：

- `frontend/src/components/chat/MessageItem.vue`
- `frontend/src/composables/useChatWorkspace.ts`
- `app/services/knowledge_base.py`
- `app/services/llm_streaming.py`

解决办法：

- `useChatWorkspace.ts` 继续按流式事件收集 `reasoningParts`。
- `MessageItem.vue` 展示时把 `reasoningParts` 合并成一个 `assistantReasoningText`。
- CSS 增加 `overflow-wrap: anywhere` 和 `word-break: break-word`，防止长文本或异常 token 撑破布局。

现在的理解：

```text
后端仍然保存原始 reasoning delta
前端展示时合并成一段可读文本
这样既不丢失流式信息，也不会让 UI 一字一行
```

### 2. qwen-max 选择“深度”但没有思考片段

表现：

- 使用 `qwen-max`，消息诊断显示 `thinking=deep`。
- 但是没有“思考片段”折叠区。
- 换成 `qwen3.7-plus` 后，能看到思考片段。

原因：

- “前端选择深度模式”和“模型返回可展示 reasoning 内容”不是同一件事。
- 之前系统把整个 `qwen` provider 都默认当成支持 `enable_thinking / thinking_budget` 的模型。
- 这会导致 `qwen-max` 也被当成“会返回原生思考片段”的模型，但实际它在当前调用方式下不返回可展示的 reasoning delta。
- `qwen3.7-plus` 属于 `qwen3*` 系列，当前更适合启用千问 thinking 参数。

涉及文件：

- `app/services/llm_provider_mapping.py`
- `app/services/knowledge_base.py`
- `frontend/src/components/chat/MessageItem.vue`
- `frontend/src/components/chat/ModelHealthPanel.vue`

解决办法：

- `qwen` provider 默认不再全局声明 `thinking_style="qwen"`。
- 只对 `qwen3*`、`qwq*`、`qvq*` 这类模型开启：
  - `thinking_style="qwen"`
  - `supports_thinking_budget=true`
  - `deep_thinking_budget=QWEN_DEEP_THINKING_BUDGET`
- `qwen-max` 仍然可以选择 UI 上的“深度”模式，但后端只会给更完整回答的系统提示，不再强行传 `enable_thinking`。
- 如果用户选了 deep，但当前模型没有声明原生 reasoning 参数能力，`model_diagnostics.warnings` 会提示：

```text
当前模型未声明支持原生深度思考参数，后端会保留更完整回答提示，但不保证返回可展示的思考片段。
```

现在的能力判断：

```text
qwen-max
  -> provider=qwen
  -> native web search: yes
  -> image input: no
  -> responses api: no
  -> native thinking budget: no

qwen3.7-plus
  -> provider=qwen
  -> native web search: yes
  -> image input: yes
  -> responses api: yes
  -> native thinking budget: yes
```

白话理解：

```text
qwen-max：可以让它回答得更认真，但不保证它吐出可展示的思维链。
qwen3.7-plus：当前系统按千问 thinking 模型处理，所以能接住 reasoning 片段。
```

### 3. qwen-max 图片输入显示“否”

表现：

- 模型健康检查里 `qwen-max` 的“图片输入”为“否”。
- 粘贴图片后，助手提示模型未声明支持原生图片输入。

原因：

- 用户贴的官方示例使用的是 `qwen3.7-plus`，不是 `qwen-max`。

- 如果系统把所有 `qwen*` 都标成图片模型，文本模型可能会在 provider 侧报错。

涉及文件：

- `app/services/llm_provider_mapping.py`
- `app/services/knowledge_base.py`
- `frontend/src/components/chat/ChatComposer.vue`
- `frontend/src/components/chat/MessageItem.vue`
- `.env`
- `.env.example`

解决办法：

- 保持 `qwen-max` 默认不声明图片输入。
- 把 `qwen3.7-plus` 加入 `AVAILABLE_MODELS`，并由能力表自动识别为图片模型。
- `qwen-vl*`、`qwen-omni*`、`qwen3.7-plus`、`qwen3.7-max` 等模型自动标记 `supports_multimodal_input=true`。
- 如果后续确认某个账号里的 `qwen-max` 版本确实支持图片，可以用配置覆盖：

### 5. 千问联网看起来开了，但天气问题没有查到

表现：

- 问“北京今天天气怎么样”。
- 模型回答说“我没有直接获取到天气信息”。
- 之前有时还会显示工具调用 `search_web`，但没有结果。

原因：

- 诊断里如果是 `nativeWeb=off, externalWeb=off`，说明这次请求实际没有启用联网。
- 之前后端即使 `.env` 里 `WEB_SEARCH_PROVIDER=none`，也会把 `search_web` 工具暴露给模型。
- 模型调用了 `search_web`，但后端没有外部搜索服务，结果只能返回空列表。
- 这会造成“看起来调用了工具，实际没有搜索结果”的假联网体验。

涉及文件：

- `frontend/src/composables/useChatWorkspace.ts`
- `frontend/src/components/chat/ChatComposer.vue`
- `app/services/tools.py`
- `app/services/knowledge_base.py`
- `app/services/llm_provider_mapping.py`
- `.env`
- `.env.example`

解决办法：

- 当前模型支持原生联网时，前端默认打开 `nativeWebSearchEnabled`。
- `ToolRegistry` 只有在外部搜索服务真正可用，并且用户开启外部联网时，才注册 `search_web`。
- 千问 Chat Completions 原生联网会传：

```python
extra_body["enable_search"] = True
extra_body["search_options"] = {
    "forced_search": True,
    "enable_search_extension": True,
}
```

注意：

- `nativeWeb=on` 代表已经把 provider 原生联网参数传给模型。
- 如果 provider 不接受某个扩展参数，后端会 fallback，并在 `model_diagnostics.warnings` 里说明。
- 如果想要稳定、可追溯的网页来源，后续仍建议配置 `WEB_SEARCH_PROVIDER=serper` 或 `tavily`，走系统外部搜索。

### 7. 流式回答正文结束后仍卡在模型诊断区，深度思考更明显

表现：

- 模型正文已经回答完了。
- 页面底部还停在类似下面这段诊断信息，光标继续闪，感觉像“没结束”：

```text
模型：qwen3.7-plus | tokens 输入/输出/总计：... | provider=qwen ...
接口：chat_completions
思考：deep
```

- 非深度模式结束得比较快；只要选择深度思考，尾巴就更容易卡十几秒。

原因：

- 前端不是自己卡住，而是在等后端发送最终 `done` 事件。
- 后端 `stream_answer()` 已经把正文通过 `content_delta` 一段段发给前端了。
- 但旧逻辑在正文流完之后，又调用了一次 `_polish_answer(...)` 做二次润色。
- 这次二次润色是一次新的非流式模型调用，不会继续向前端吐字。
- 所以前端看起来就是“正文已经结束，但流式状态还没结束”。
- 深度思考模式下 `_should_polish_answer(...)` 更容易返回 true，所以这个问题在 deep 模式下更明显。

涉及文件：

- `app/services/knowledge_base.py`
- `frontend/src/composables/useChatWorkspace.ts`
- `frontend/src/components/chat/MessageItem.vue`

解决办法：

- 保留非流式 `/api/chat` 的二次润色逻辑。
- 流式 `/api/chat/stream` 不再在正文流完之后同步调用 `_polish_answer(...)`。
- provider stream 一结束，后端立即整理 usage、diagnostics、reasoning_parts，然后发送 `done`。
- 前端收到 `done` 后，`useChatWorkspace.ts` 会把当前消息的 `streaming=false`，`MessageItem.vue` 的光标也会消失。

白话理解：

```text
旧逻辑：
模型边说边显示 -> 正文显示完 -> 后端又偷偷问一次模型润色 -> 前端干等 done

新逻辑：
模型边说边显示 -> 正文显示完 -> 后端立刻发 done -> 前端马上结束流式状态
```

### 8. 本轮修复后的快速判断方式

以后看一条回答是否真的启用了某个能力，优先看助手消息底部诊断：

```text
provider=qwen
requested=qwen-max
resolved=qwen-max
nativeWeb=on/off
externalWeb=on/off
thinking=deep/quick
接口: chat_completions / qwen_responses / qwen_responses_stream
warnings: 是否发生参数 fallback 或能力降级
```

不要只看“UI 按钮是否打开”。UI 按钮表示用户意图，`model_diagnostics` 才表示这次后端真实执行结果。

也就是说，现在系统不是只绑定某一个云厂商，而是先通过 `LLMProviderAdapter` 隔离 provider 调用，再由当前的 OpenAI-compatible adapter 绑定在“OpenAI 兼容的 Chat Completions 协议”上。DeepSeek、千问百炼、Kimi、混元、硅基流动、千帆、OpenAI、自建 OpenAI 网关，只要提供类似：

```text
POST {base_url}/chat/completions
model=xxx
messages=[...]
```

这种接口，就可以被系统接入。

本地部署时常见的兼容方式是：

- `vLLM`：开启 OpenAI-compatible server
- `Ollama`：使用 OpenAI 兼容接口
- `LM Studio`：本地 OpenAI-compatible server
- `Xinference` / `FastChat` / 自建网关：对外包装成 OpenAI Chat Completions
- 公司内部模型服务：在网关层把内部协议转换成 OpenAI 兼容协议

如果以后本地模型是这种形式：

```text
LOCAL_MODEL_BASE_URL=http://127.0.0.1:8001/v1
LOCAL_MODEL_NAME=qwen2.5-7b-instruct
```

那么理论上只需要把它加入 `.env` 的 provider 配置或 `EXTRA_PROVIDER_CONFIGS_JSON`，再通过 `MODEL_PROVIDER_OVERRIDES_JSON` 指定模型归属即可。

但是如果本地模型只有非 OpenAI 风格接口，比如：

```text
POST /generate
payload={prompt, sampling_params}
```

或者只能通过某个 Python SDK 直接调用，那么当前这套 `OpenAI(...)` client 就不能直接调用，需要新增一个 provider client 适配层。建议后续抽象成：

```text
LLMProviderAdapter
├─ OpenAICompatibleAdapter
├─ LocalNativeAdapter
├─ ResponsesApiAdapter
└─ VendorSdkAdapter
```

这样产品层仍然使用统一的参数，例如 `model`、`messages`、`stream`、`thinking_mode`、`native_web_search`，底层由不同 adapter 翻译成不同厂商或本地模型真正需要的格式。

所以更准确地说：

```text
当前兼容对象：OpenAI 兼容接口
未来本地部署：只要本地模型也提供 OpenAI 兼容接口，就不需要大改
非兼容本地接口：需要新增 provider adapter，但上层产品设计可以继续复用
```

### 问题 2：多轮、流式、深度思考、工具调用、多模态等能力，当前是怎么兼容设计的？

当前系统的兼容设计分成三层。

第一层是“模型 / provider 路由”。

这里的 `provider` 不是“模型本身”，而是“模型背后的服务商 / 接口入口”。
你可以把它理解成：

```text
前端选模型 qwen-max
  -> 后端判断它属于 qwen provider
  -> 再去拿 QWEN_BASE_URL / QWEN_API_KEY
  -> 最后把请求发给千问的 OpenAI 兼容接口
```

所以这一层真正解决的是：

- 前端选了什么模型
- 这个模型应该路由到哪个服务商
- 这个服务商的 base_url 和 api_key 是什么
- 这个模型最终要不要做手工覆盖映射

简单说，它负责“选哪家、走哪条接口、用哪套凭证”。
这也是为什么我把它放在第一层。

而 `LLMProviderAdapter` 是下一步要补上的“请求翻译层”。
它不是再做一次 provider 选择，而是把：

- `thinking_mode=deep`
- `native_web_search=true`
- `stream=true`

这些产品层统一参数，翻译成不同 provider 真正认识的参数格式。

例如同样是“深度思考”：

- DeepSeek 可能要 `extra_body={"thinking": {"type": "enabled"}}` 再配 `reasoning_effort`
- 千问可能要 `extra_body={"enable_thinking": True, "thinking_budget": 2048}`
- 以后本地模型如果有自己的思考参数，就再单独加一个 adapter

如果不把这一层拆出来，所有 provider 的差异都会继续堆在 `knowledge_base.py` 里的同一条 `OpenAI client` 调用上。
后面一旦要加：

- 工具调用
- 多模态消息
- Responses API
- 不同流式事件
- 不同厂商的特殊参数

这个文件就会越来越像一个“大型兼容分发器”，维护成本会很高。

所以 `LLMProviderAdapter` 的目的就是：

1. 把 provider 参数差异隔离掉
2. 让 `knowledge_base.py` 只保留业务编排
3. 让后续新增厂商或本地模型时，只需要补一个 adapter，而不是改一堆主流程代码

#### 原来 provider 是怎么做的，以及为什么现在要拆

当前这套实现其实已经有了 provider 的雏形，但它还是“挂在 OpenAI client 上做适配”。
可以把它理解成下面这条链路：

```python
provider, client = self._resolve_model_client(model_name)
options = self._completion_options(
    model_name=model_name,
    provider=provider,
    thinking_mode=thinking_mode,
    stream=stream,
    native_web_search=native_web_search,
)

kwargs = {
    "model": model_name,
    "messages": messages,
    "stream": stream,
    **options,
}

return client.chat.completions.create(**kwargs)
```

如果 provider 不接受扩展参数，就会走降级重试：

```python
fallback_kwargs = {
    "model": model_name,
    "messages": messages,
    "stream": stream,
    "temperature": self.settings.temperature,
    "max_tokens": self.settings.max_tokens,
}
return client.chat.completions.create(**fallback_kwargs)
```

这套做法的优点是简单，能快速把 DeepSeek、千问、OpenAI 这类 OpenAI-compatible 服务接起来。
但缺点也很明显：

1. **所有 provider 最后都挤进同一个 `OpenAI client` 调用**
   - 只要是 OpenAI-compatible，就能用
   - 但如果某个模型只有原生 SDK，或者以后要接 Responses API、原生 tool loop，就会很别扭

2. **provider 差异和业务编排混在一个服务里**
   - 路由模型、拼装参数、回退重试、做 RAG、做流式输出，全都在 `knowledge_base.py` 这一条主链路上
   - 以后 provider 一多，这个文件会越来越像“兼容参数大杂烩”

3. **扩展参数失败会被同 provider/model 重试，容易让能力悄悄变弱**
   - 例如原来想启用 `enable_thinking` 或 `enable_search`
   - provider 不认这些参数时，系统会去掉参数再试一次
   - 这能保证回答不中断，但也意味着“界面上开了深思 / 联网，实际可能没有生效”

4. **重构前还没有把 provider 原生事件抽象出来**
   - 原来流式主要只消费 `delta.content`
   - 原来 `reasoning_content` 会被跳过
   - 原来 `tool_calls`、多模态 message parts、Responses API 也还没进统一模型
   - 现在已经补上统一 `StreamingEvent`、reasoning 展示与保存、tool calling 闭环、多模态 message part，以及千问 Responses API 非流式和基础流式 adapter

所以现在要引入 `LLMProviderAdapter`，本质上是把“已经能跑的兼容写法”升级成“可扩展的正式分层”。
这样以后新增能力时，改动会更集中：

- `knowledge_base.py` 继续负责 RAG 编排
- adapter 负责 provider 参数翻译
- registry 负责模型能力声明
- 以后再加工具调用、多模态、Responses API，也不会把主流程冲烂

代码位置主要是：

- `app/services/knowledge_base.py::_resolve_provider_name()`
- `app/services/knowledge_base.py::_resolve_model_provider()`
- `app/services/knowledge_base.py::_resolve_model_adapter()`
- `app/services/llm_provider_adapter.py::LLMProviderAdapterFactory`
- `.env` 中的 `AVAILABLE_MODELS`
- `.env` 中的 `MODEL_PROVIDER_OVERRIDES_JSON`
- `.env` 中的 `EXTRA_PROVIDER_CONFIGS_JSON`

作用是回答：

```text
前端选择 qwen-max
后端应该用哪个 provider？
base_url 是哪个？
api_key 从哪里取？
最终传给供应商的 model 名是什么？
```

例如：

```text
qwen-max       -> provider=qwen      -> QWEN_BASE_URL
deepseek-v4   -> provider=deepseek  -> DEEPSEEK_BASE_URL
gpt-4o-mini   -> provider=openai    -> OPENAI_BASE_URL
```

如果模型名前缀无法准确判断，就用 `MODEL_PROVIDER_OVERRIDES_JSON` 手工指定。

#### 设计模式对照（复习版）

这一段可以直接当后面复习用的速记卡。它不是在背名词，而是把当前代码和常见设计模式对应起来。

##### 1. 模板方法模式

基本概念：

- 定义一个固定的流程骨架。
- 把其中少数步骤留给具体实现去变化。
- 核心就是“主流程固定，局部步骤可替换”。

在这个项目里的对应：

- `KnowledgeBaseService.answer()`
- `KnowledgeBaseService.stream_answer()`
- `KnowledgeBaseService._chat_completion()`

它们固定了主链路：

```text
解析模型 -> 解析 provider -> 组装参数 -> 调用模型 -> 降级重试 -> 归一化结果 -> 返回前端
```

怎么用：

- 适合业务主流程已经稳定，但局部步骤会变化的场景。
- 常见于 RAG、工作流、ETL、消息编排、任务流水线。

在这里它的作用是：

- 让 RAG 主流程稳定下来。
- 让 provider 差异只影响局部步骤。
- 避免业务逻辑散成很多 if/else。

Java 伪代码可以这样理解：

```java
// 抽象类：定义固定流程骨架
public abstract class KnowledgeBaseWorkflow {

    // 模板方法：主流程固定，不建议子类改掉
    public final AnswerResult answer(String question) {
        String provider = resolveProvider(question);   // 固定步骤1
        Map<String, Object> options = buildOptions(provider); // 固定步骤2
        RawResponse raw = callModel(provider, options); // 固定步骤3
        return normalize(raw);                          // 固定步骤4
    }

    // 局部变化步骤：交给子类实现
    protected abstract String resolveProvider(String question);
    protected abstract Map<String, Object> buildOptions(String provider);
    protected abstract RawResponse callModel(String provider, Map<String, Object> options);
    protected abstract AnswerResult normalize(RawResponse raw);
}

// 子类1：DeepSeek 的实现
public class DeepSeekWorkflow extends KnowledgeBaseWorkflow {
    @Override
    protected String resolveProvider(String question) {
        return "deepseek";
    }

    @Override
    protected Map<String, Object> buildOptions(String provider) {
        Map<String, Object> options = new HashMap<>();
        options.put("thinking", Map.of("type", "enabled"));
        options.put("reasoning_effort", "high");
        return options;
    }

    @Override
    protected RawResponse callModel(String provider, Map<String, Object> options) {
        // 调用 DeepSeek 的 OpenAI-compatible 接口
        return new RawResponse();
    }

    @Override
    protected AnswerResult normalize(RawResponse raw) {
        return new AnswerResult();
    }
}

// 子类2：Qwen 的实现
public class QwenWorkflow extends KnowledgeBaseWorkflow {
    @Override
    protected String resolveProvider(String question) {
        return "qwen";
    }

    @Override
    protected Map<String, Object> buildOptions(String provider) {
        Map<String, Object> options = new HashMap<>();
        options.put("enable_thinking", true);
        options.put("thinking_budget", 2048);
        return options;
    }

    @Override
    protected RawResponse callModel(String provider, Map<String, Object> options) {
        // 调用千问的 OpenAI-compatible 接口
        return new RawResponse();
    }

    @Override
    protected AnswerResult normalize(RawResponse raw) {
        return new AnswerResult();
    }
}
```

这里要注意两点：

1. `answer()` 是 `final`，表示主流程不让子类随便改。
2. `resolveProvider()`、`buildOptions()`、`callModel()`、`normalize()` 这些步骤交给子类变。

所以模板方法模式的关键不是“没有接口”，而是：

- 用抽象类或父类把主流程固定住
- 用抽象方法 / protected 方法把可变步骤留出来
- 子类只负责局部差异，不负责重写整个流程

如果你把它放到咱们项目里理解，就相当于：

```text
主流程固定：先路由 provider -> 再组参数 -> 再调用模型 -> 再降级/归一化
局部可变：DeepSeek 怎么拼参数、Qwen 怎么拼参数、本地模型怎么拼参数
```

##### 2. 适配器模式

基本概念：

- 把一个接口转换成另一个接口。
- 让不兼容的系统能一起工作。
- 本质上是在做“翻译”。

在这个项目里的对应：

- `DeepSeekOptionsAdapter`
- `QwenOptionsAdapter`
- 以后要正式抽出来的 `LLMProviderAdapter`

它们做的事情就是把统一语义翻译成 provider 真正认识的参数：

```text
thinking_mode=deep
  -> DeepSeek: extra_body["thinking"] + reasoning_effort
  -> Qwen: extra_body["enable_thinking"] + thinking_budget
```

怎么用：

- 当上层参数统一，但底层协议不同的时候，用适配器。
- 适合第三方 API、旧系统兼容、新旧协议过渡。

在这里它的作用是：

- 前端不用理解 DeepSeek 和千问的细节差异。
- `knowledge_base.py` 不用堆大量厂商分支。
- 新增 provider 时只补适配器，不必重写主流程。

##### 3. 策略模式

基本概念：

- 把一组可替换算法封装起来。
- 运行时按条件选择不同策略。
- 核心是“同一个目标，不同实现”。

在这个项目里的对应：

- `build_provider_options()`
- `CapabilityRegistry`
- `_resolve_web_search_plan()`
- `thinking_mode=quick/deep`

它们本质上在决定：

```text
这个模型支持什么？
这次该用哪种思考参数？
要不要开原生联网？
要不要退回外部搜索？
```

怎么用：

- 当同一个目标有多种执行方式时，用策略模式。
- 比如排序、检索、推荐、风控、支付、搜索策略。

在这里它的作用是：

- DeepSeek 和千问可以走不同能力策略。
- `native_web_search` 和 `external_web_search` 可以按能力切换。
- 同一个前端开关，后端可以按 provider 动态处理。

##### 4. 工厂 / 注册表模式

基本概念：

- 负责创建对象或解析对象归属。
- 把“怎么创建”隐藏起来。
- 上层只拿结果，不关心构造细节。

在这个项目里的对应：

- `_resolve_provider_name()`
- `_resolve_model_provider()`
- `_resolve_model_adapter()`
- `_resolve_model_provider_config()`
- `LLMProviderAdapterFactory`
- `CapabilityRegistry`

它们本质上在做“这个模型属于谁、该怎么实例化 client、该用什么配置”的解析。

怎么用：

- 当对象创建逻辑比较复杂时，用工厂或注册表集中处理。
- 可以减少业务代码里的 if/else 散落。

在这里它的作用是：

- `qwen-max` 自动找到千问配置。
- `deepseek-v4` 自动找到 DeepSeek 配置。
- 新增模型时只改映射，不用改一堆调用点。

##### 5. 组合起来怎么看

这几个模式在当前项目里不是分开的，而是组合起来工作的：

```text
工厂 / 注册表
  -> 先决定 provider 和 client

策略
  -> 决定这次用什么能力参数

适配器
  -> 把统一语义翻译成 provider 真正认识的参数

模板方法
  -> 维持完整 RAG 和回答编排主流程
```

所以你现在看到的不是单独一个模式，而是“固定主流程 + 一组可替换策略 + 一层参数适配 + 一层对象解析”的组合。

##### 6. 为什么要正式化 `LLMProviderAdapter`

因为当前代码虽然已经有这些模式的影子，但它们还散着：

- 路由散在 `_resolve_provider_name()`
- 参数翻译散在 `llm_provider_mapping.py`
- 回退逻辑散在 `_chat_completion()`
- 业务编排散在 `knowledge_base.py`

这会导致后面加新能力时，模式还在，但代码组织不够清晰。
所以正式抽成 `LLMProviderAdapter`，就是把“已经存在的模式”显式化，让后面扩展更稳。

第二层是“模型能力注册表”。

代码位置：

- `app/services/llm_provider_mapping.py::ModelCapability`
- `app/services/llm_provider_mapping.py::CapabilityRegistry`
- `.env` 中的 `MODEL_CAPABILITIES_JSON`

它描述一个模型或 provider 支持什么能力，例如：

```text
supports_native_web_search：是否支持模型原生联网
thinking_style：深度思考参数风格，none / deepseek / qwen
supports_reasoning_effort：是否支持 reasoning_effort
supports_thinking_budget：是否支持 thinking_budget
deep_reasoning_effort：深度思考强度
deep_thinking_budget：千问思考预算
```

当前默认能力大致是：

```text
deepseek:
  thinking_style=deepseek
  supports_reasoning_effort=true
  supports_native_web_search=false

qwen:
  thinking_style=qwen
  supports_thinking_budget=true
  supports_native_web_search=true
```

如果某个具体模型能力和默认值不一样，可以通过 `MODEL_CAPABILITIES_JSON` 覆盖。

第三层是“统一产品参数 -> 厂商真实参数”的转换。

代码位置：

- `app/services/llm_provider_mapping.py::CanonicalCompletionOptions`
- `app/services/llm_provider_mapping.py::DeepSeekOptionsAdapter`
- `app/services/llm_provider_mapping.py::QwenOptionsAdapter`
- `app/services/llm_provider_mapping.py::ProviderOptionsAdapter`

前端只需要表达产品语义：

```text
thinking_mode=quick/deep
native_web_search=true/false
external_web_search=true/false
stream=true/false
```

后端再按 provider 翻译。

DeepSeek 深度思考会被翻译成类似：

```python
extra_body = {"thinking": {"type": "enabled"}}
reasoning_effort = "high"
```

千问深度思考会被翻译成类似：

```python
extra_body = {
    "enable_thinking": True,
    "thinking_budget": 2048
}
```

千问原生联网会被翻译成类似：

```python
extra_body = {
    "enable_search": True
}
```

流式输出会统一加：

```python
stream=True
stream_options={"include_usage": True}
```

这样做的好处是：前端不需要知道 DeepSeek 和千问的参数差异，前端只关心“快速 / 深度”“是否联网”“是否流式”。

当前能力支持状态如下：

| 能力 | 当前状态 | 当前实现方式 | 注意事项 |
| --- | --- | --- | --- |
| 多轮对话 | 已支持 | `ChatMemoryService` 使用 MySQL 保存会话和消息，Redis 缓存最近消息；请求时通过 `resolve_history()` 取最近上下文 | 当前不是把所有历史消息原样作为多条 provider `messages` 传入，而是把历史整理进 RAG prompt 的 `Conversation history` |
| 流式输出 | 已支持增强版 | `/api/chat/stream` 使用 SSE；后端 `stream_answer()` 读取 provider stream，前端 `chatStream()` 逐段渲染 | 除正文 `delta` 外，已经能接收 `reasoning_delta`、`tool_call_delta`、`usage`、`diagnostics` |
| 深度思考 | 部分支持 | UI 选择 `quick/deep`，后端按 DeepSeek / Qwen 参数风格映射 | 参数是否真的生效要看 `model_diagnostics.warnings` |
| 思考过程展示 | 基础版已接入 | 后端流式时把 `reasoning_content` 转成 `reasoning_delta`，前端收集到助手消息的折叠区，最终会写入聊天记忆 `meta_json.reasoning_parts` | 只展示 provider 明确返回的 reasoning 片段；不是所有模型都会返回 |
| 原生联网 | 部分支持 | `native_web_search` 按模型能力映射到 provider 参数；千问默认标记支持 | 原生联网来源通常是供应商黑盒，不一定返回结构化引用 |
| 外部联网 | 已预留 / 可配置 | `WEB_SEARCH_PROVIDER=serper/tavily` 时，后端自己检索并拼进上下文 | 比原生联网更容易做结构化引用和可追溯来源 |
| 工具调用 | 已接入增强版 | `ToolRegistry` 提供只读工具，非流式 `/api/chat` 和流式 `/api/chat/stream` 都接入 tool_calls 循环 | 当前只开放知识库搜索和网页搜索；前端会把工具调用放在助手消息折叠区 |
| 多模态输入 | 基础版已接入增强版 | `ChatRequest` 新增 `message_parts`，支持 `text`、`image_url`、`file_ref`；provider message 可传 OpenAI-compatible `image_url` part | 前端已提供轻量引用入口，可从文档库选择 `file_ref`，也可添加图片 URL，输入框也支持直接粘贴图片；不支持图片的 provider 会自动降级成纯文本描述 |
| 图文混合输出 | 暂不支持专门处理 | 如果模型返回 Markdown/HTML，前端目前按普通文本 / Markdown 思路展示 | 千问 `enable_text_image_mixed` 这类参数还没有纳入能力映射 |
| Responses API | 千问基础版已接入增强版 | 新增 `QwenResponsesProviderAdapter`，`QWEN_RESPONSES_API_ENABLED=true` 且启用千问原生联网时优先走 `client.responses.create(..., tools=[{"type": "web_search"}])`；流式请求会走 `stream=True` 并转换回系统内部兼容的 chat stream 形态 | 默认关闭；失败会退回 Chat Completions；`web_extractor`、`code_interpreter`、Responses 原生复杂事件还未完整接入 |
| 模型能力自动匹配 | 基础版已接入 | `ModelCapability` 新增 `supports_tool_calling`、`supports_multimodal_input`、`supports_responses_api`、`supports_responses_streaming`，并可通过 `MODEL_CAPABILITIES_JSON` 覆盖 | 后端会按能力自动跳过工具、把图片 URL 降级成文本引用、或把 Responses API 回退到 Chat Completions |

所以这套系统现在的设计方向是对的：**先把产品层能力抽象成统一参数，再由 provider adapter 翻译成厂商参数。**

但目前还不是所有模型能力都做完了。最核心的“多轮、流式、深度思考参数映射、模型诊断、原生/外部联网开关、只读工具调用闭环、多模态 message part 协议、轻量附件入口、图片粘贴、reasoning / tool_call 折叠展示、千问 Responses API 非流式与基础流式 adapter、模型能力自动匹配与降级”已经有了；“图片/文件上传到对象存储并生成公网 URL、Responses API 原生复杂事件、web_extractor / code_interpreter 等更多原生工具”还需要后续继续补。

### 问题 3：下面这些厂商示例，当前系统是否兼容？

#### ① 多轮对话

DeepSeek 和千问示例里都是手动维护：

```python
messages.append({"role": "user", "content": "..."})
messages.append({"role": "assistant", "content": "..."})
```

当前系统**支持多轮上下文效果**，但实现方式和示例不完全一样。

当前系统链路是：

```text
前端当前会话 messages
  -> 请求 /api/chat/stream 时携带最近 history
  -> 后端 ChatMemoryService 根据 conversation_id 从 Redis/MySQL 取最近消息
  -> KnowledgeBaseService 把历史整理进 Conversation history
  -> 和 RAG 检索上下文一起发给模型
```

也就是说，用户可以连续追问，系统会知道最近上下文。

但当前传给 provider 的最终结构更接近：

```python
messages = [
    {"role": "system", "content": "...系统规则..."},
    {"role": "user", "content": "Question + Conversation history + Knowledge-base context"}
]
```

而不是完全像厂商示例那样：

```python
messages = [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."},
    {"role": "user", "content": "..."}
]
```

这样做更适合 RAG，因为可以把“历史问题 + 当前问题 + 知识库片段 + 引用规则”合并成一个更可控的提示词。缺点是如果后续要支持原生 tool_calls 或多模态 message parts，就需要把历史消息结构化程度再提高。

#### ② 流式输出

厂商示例的核心是：

```python
stream=True
for chunk in response:
    ...
```

当前系统**已经兼容流式输出**。

后端：

```text
app/services/knowledge_base.py::stream_answer()
```

会调用：

```python
adapter.create_chat_completion(..., stream=True)
```

当前第一阶段仍然由 `OpenAICompatibleProviderAdapter` 在内部调用 `client.chat.completions.create(..., stream=True)`，然后 `KnowledgeBaseService.stream_answer()` 把模型增量包装成 SSE：

```text
type=delta
type=done
```

前端：

```text
frontend/src/api.ts::chatStream()
frontend/src/composables/useChatWorkspace.ts::sendChat()
```

会逐段接收并渲染到聊天气泡中。

需要注意的是，DeepSeek / 千问示例里的：

```python
delta.reasoning_content
```

当前系统已经做了基础展示：后端遇到 provider 返回的 `reasoning_content` 时，不再直接跳过，而是转成统一的 `reasoning_delta` 流式事件；前端收到后会把它收集到助手消息的“思考过程”折叠区里，最终还会随 `done` 事件里的 `reasoning_parts` 写入聊天记忆。

这里要注意两点：

- 不是所有模型都会返回 `reasoning_content`，所以有些模型即使开了深度模式，也可能没有可展示的思考片段。
- 当前展示的是 provider 明确返回的 reasoning 片段；系统不会自己伪造“思考过程”。

所以结论是：

```text
流式最终回答：已支持
流式 usage：尽量支持，provider 返回 usage 时会记录，否则后端估算
流式 reasoning_content 单独展示：基础版已支持，会进入前端折叠区并保存到聊天记忆
```

#### ③ 深度思考

DeepSeek 示例里的：

```python
reasoning_effort="high"
extra_body={"thinking": {"type": "enabled"}}
```

当前系统在 `thinking_mode=deep` 且 provider 为 DeepSeek 时会做类似映射。

千问示例里的：

```python
extra_body={"enable_thinking": True}
stream_options={"include_usage": True}
```

当前系统在 `thinking_mode=deep` 且 provider 为 Qwen 时也会做类似映射，并且会带上 `thinking_budget`。

前端对应入口是聊天设置里的“快速 / 深度”模式；请求字段是：

```json
{
  "thinking_mode": "deep"
}
```

后端返回的 `model_diagnostics` 可以确认本次后端认为自己用了什么：

```json
{
  "provider": "qwen",
  "requested_model": "qwen-max",
  "resolved_model": "qwen-max",
  "thinking_mode": "deep",
  "option_fallback_used": false,
  "warnings": []
}
```

如果某个模型或网关不接受这些扩展参数，后端会用同一个 provider/model 去掉扩展参数重试，并把 warning 返回给前端。这个时候不代表切换成 DeepSeek 了，只代表“深度思考或原生联网参数可能没有生效”。

#### ④ 工具调用

厂商示例里的 Function Calling / Tool Calls 需要完整链路：

```text
1. 请求时传 tools=[...]
2. 模型返回 tool_calls
3. 后端识别 tool_calls
4. 后端执行真实函数
5. 把 role=tool 的结果再发回模型
6. 模型生成最终自然语言回答
```

当前系统**已经接入基础工具调用闭环**，但只开放只读工具。

现在的实现方式是：

- `app/services/tools.py` 提供 `ToolRegistry`
- `search_knowledge_base` 用来按当前用户、会话范围检索知识库
- `search_web` 用来走外部网页搜索配置
- 非流式 `/api/chat` 会进入 `_chat_completion_with_tools()`
- 流式 `/api/chat/stream` 会进入 `_stream_completion_with_tools()`
- provider 支持 `tools` 时，后端会传 `tools=[...]` 和 `tool_choice="auto"`
- 模型返回 `tool_calls` 后，后端执行工具，再把 `role=tool` 结果回传模型
- 最多执行 2 轮工具调用，避免模型无限循环
- 工具调用过程会写入 `model_diagnostics.tool_calls`，流式时还会发出 `tool_call_delta`

当前链路可以理解成：

```text
ToolRegistry
├─ search_knowledge_base
├─ web_search
├─ document_lookup
├─ file_open
└─ custom_business_tool

Chat Loop
├─ 第一次请求模型，带 tools
├─ 如果返回 tool_calls，执行工具
├─ 写入 role=tool 结果
├─ 再请求模型生成最终回答
└─ 保存 tool 调用过程和最终消息
```

当前工具边界是保守的：模型只能调用只读工具查资料，不能删除文件、修改文件、写数据库。后续如果要开放文件编辑、删除、写入业务系统这类高风险工具，必须额外做权限控制、审计记录和人工确认。

#### ⑤ 多模态

如果厂商示例使用图片、音频、文件等多模态输入，一般会出现类似：

```python
messages=[
  {
    "role": "user",
    "content": [
      {"type": "text", "text": "..."},
      {"type": "image_url", "image_url": {"url": "..."}}
    ]
  }
]
```

第四阶段基础版后，当前系统**已经具备多模态聊天输入的后端协议**。

当前接口定义是：

```python
class ChatMessagePart(BaseModel):
    type: Literal["text", "image_url", "file_ref"]
    text: str | None = None
    image_url: str | None = None
    file_id: int | None = None
    file_name: str | None = None
    mime_type: str | None = None

class ChatRequest(BaseModel):
    question: str
    message_parts: list[ChatMessagePart] = []

class ChatHistoryItem(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: str
```

也就是说，旧的 `question: str` 仍然保留，保证现在的聊天输入框不用改也能继续跑；新的 `message_parts` 用来承载更结构化的输入。

当前支持的 part 是：

```text
ChatMessagePart
├─ text
├─ image_url
└─ file_ref
   ├─ file_id
   ├─ file_name
   └─ mime_type
```

后端处理方式是：

```text
纯文本请求：
  question -> RAG prompt -> provider

带 message_parts 的请求：
  message_parts -> 归一化
  -> text/file_ref 转成可检索的 prompt 文本
  -> image_url 按 OpenAI-compatible image_url part 传给 provider
  -> 如果 provider 不支持多模态，则 adapter 自动降级成纯文本描述重试
```

第四阶段增强后，前端已经补了一个轻量入口：

```text
ChatComposer
  -> 引用按钮
  -> 从文档库选择文件，生成 file_ref
  -> 输入图片 URL，生成 image_url
  -> 或者在聊天输入框直接粘贴图片，生成 data:image/... 形式的 image_url
  -> 发送时和 question 一起组成 message_parts
```

所以现在不是“只能后端支持、前端发不出去”了。
用户可以在聊天输入框里选择已有文档、贴一个图片 URL，或者直接 `Ctrl+V` 粘贴截图/图片；发送后用户消息下面会显示对应引用 chip；聊天记忆里也会保存这次消息的 `message_parts`。

这里要注意一个命名点：后端字段仍然叫 `image_url`，并不是说只能填公网 URL。
在 OpenAI-compatible 的消息协议里，图片输入常见有两种写法：

```text
公网图片：
image_url.url = "https://example.com/a.png"

粘贴图片 / 本地图片转码：
image_url.url = "data:image/png;base64,...."
```

所以“直接粘贴图片”的前端实现，本质是：

```text
用户 Ctrl+V 图片
  -> 浏览器从剪贴板拿到 File
  -> FileReader 转成 data:image/...;base64,...
  -> 放入 message_parts[].image_url
  -> 后端按模型能力决定是否原生传给 provider
```

但它仍然只是“轻量附件入口”，不是完整的网盘式上传和多模态资源管理。生产级图片输入建议再补一层：图片上传到后端或对象存储，生成公网可访问 URL，再交给云模型。这样更适合大图片、长期保存和厂商对 data URL 不兼容的场景。

白话理解：

```text
原来：
聊天请求只有一根字符串 question。
模型只能收到文字。

现在：
聊天请求还是保留 question；
但旁边多了一个 message_parts 数组。
这个数组可以放文字、图片 URL、文件引用。

后端会把它分两路用：
1. 用文本化内容做检索和 RAG prompt
2. 对支持图片的 OpenAI-compatible provider，额外传 image_url part
```

当前边界：

- 前端 API 类型已支持 `message_parts`
- 前端 `ChatComposer` 已支持从文档库选择 `file_ref`
- 前端 `ChatComposer` 已支持添加图片 URL
- 前端 `ChatComposer` 已支持在输入框直接粘贴图片，生成 base64 data URL
- 用户消息会回显已发送的引用 chip
- 聊天历史 `meta_json` 会保存 `message_parts`
- 聊天历史接口会返回 `message_parts`
- `file_ref` 目前主要作为结构化引用进入 prompt，不等于把文件二进制直接喂给多模态模型
- 音频、视频、图片上传到对象存储、provider 原生文件 API 还没有做

#### ⑥ 千问原生联网、图文混合输出、Responses API

你贴的千问示例里还有一些能力：

```python
extra_body={"enable_search": True}
extra_body={"enable_text_image_mixed": True}
client.responses.create(..., tools=[{"type": "web_search"}])
```

当前系统状态是：

```text
enable_search：部分支持，映射为 native_web_search
enable_text_image_mixed：暂未纳入系统参数
Responses API：基础版已接入，默认关闭；打开 QWEN_RESPONSES_API_ENABLED=true 后，千问原生联网优先走 responses.create()
Responses API 流式：基础版已接入；stream=True 时会把 Responses 流事件转换成系统兼容的 chat stream chunk
web_search：Responses API 下基础接入
web_extractor / code_interpreter tools：暂未接入
```

如果只是想让千问自己联网回答，当前 `native_web_search=true` 可以尝试启用；如果想拿到稳定、可追溯、可展示引用来源，还是更建议用系统自己的 `external_web_search`，也就是 Serper / Tavily 这类外部搜索，再由 RAG prompt 显式拼接来源。
如果你想专门测试千问 Responses API，需要在 `.env` 里设置：

```env
QWEN_RESPONSES_API_ENABLED=true
```

然后前端选择千问模型，并打开原生联网。后端诊断里会出现：

```text
provider_api=qwen_responses
provider_api=qwen_responses_stream
```

如果 Responses API 调用失败，会自动回退到原来的 Chat Completions，并在 `model_diagnostics.warnings` 里记录原因。

### 总结：当前系统能力边界

一句话总结：

```text
当前系统已经具备 OpenAI 兼容模型接入、多 provider 路由、多轮上下文、流式输出、深度思考参数映射、模型诊断、原生/外部联网开关。

当前系统已经接入 provider tool calling 基础闭环、多模态 message part 基础协议、reasoning_content 可视化展示与持久化、千问 Responses API 非流式和基础流式 adapter、模型能力自动匹配与降级，但还没有完整接入图文混合输出、Responses API 原生复杂事件和更多工具。
```

如果后续继续做“模型能力兼容层”，推荐优先级是：

1. 先把 `LLMProviderAdapter` 抽象正式化，不要让所有 provider 都挤在 OpenAI client 调用里。（第一阶段已完成）
2. 增加统一 `StreamingEvent`：`content_delta`、`reasoning_delta`、`tool_call_delta`、`usage`、`diagnostics`。（第二阶段已完成基础版）
3. 增加 `ToolRegistry` 和 tool calling 循环，先做只读工具，例如知识库搜索、网页搜索、文档查询。（第三阶段增强版已完成：非流式和流式都接入）
4. 增加多模态 message part schema，让文本、图片、文件引用可以统一进入聊天请求。（第四阶段基础版已完成）
5. 对千问 Responses API 单独做 adapter，因为它和 Chat Completions 的工具/联网形态已经不是完全同一套。（第五阶段增强版已完成：非流式和基础流式都接入，默认关闭）
6. 把模型能力显式展示到前端消息和健康检查里，让 reasoning、tool calls、diagnostics 看得见。（第六阶段基础版已完成）
7. 增加模型能力自动匹配与降级，避免不支持图片、工具或 Responses API 的模型硬调用失败。（第七阶段基础版已完成）

### 当前 1-7 阶段完成确认

这七个阶段现在已经形成一个完整的基础闭环，不再只是文档设计。

也就是说，现在“模型能力兼容层”的基础版已经闭环：

```text

  -> 后端解析 provider 和 ModelCapability
```

- 当前架构已经能承接新 provider。
- 当前架构已经能承接新模型能力。
- 当前架构已经能在模型不支持某能力时可解释地降级。

### 后续如果继续做高级能力，还可以扩展哪些

后续增强建议不要再散落在 `knowledge_base.py` 里硬堆分支，而是继续沿着现在这几个层次扩。

#### 1. 图片和文件资源管理升级

当前图片粘贴走的是 `data:image/...;base64,...`，适合本地快速体验。

后续可以升级成：

- 前端粘贴 / 拖拽 / 上传图片
- 后端保存到 `data/chat_assets`、MinIO、S3、OSS 等对象存储
- 生成可访问 URL
- `message_parts[].image_url` 里放这个 URL
- 聊天历史里保存资源 ID 和 URL

这样更适合：

- 大图片
- 长期保存
- 云厂商只接受公网 URL 的场景
- 多端回看同一条带图消息

#### 2. 更完整的多模态 message part

当前 `message_parts` 支持：

```text
text
image_url
file_ref
```

后续可以扩展成：

```text
text
image_url
input_audio
input_video
file_ref
provider_file_id
document_page_ref
spreadsheet_range_ref
```

这样聊天请求就可以表达：

- 一张图片
- 一段音频
- 一个 PDF 的某几页
- 一个 Excel 的某个 sheet / range
- 一个已经上传到 provider 的文件 ID

#### 3. Responses API 原生复杂事件

当前千问 Responses API 已经能基础接入，但复杂事件还可以继续补。

后续可以进一步解析：

- 原生 `response.output_text.delta`
- 原生 reasoning 事件
- 原生 tool call 事件
- 原生 citation / reference 事件
- `web_search` 的结构化来源
- `web_extractor`
- `code_interpreter`

目标是不要只把 Responses API 转成“像 Chat Completions 的文本流”，而是尽量保留它原生的工具、引用和中间状态。

#### 4. 更多 provider 的专属 adapter

当前 `OpenAICompatibleProviderAdapter` 能覆盖大部分 OpenAI 兼容服务。

后续如果接入非兼容接口，可以新增：

```text
LLMProviderAdapter
├─ OpenAICompatibleProviderAdapter
├─ QwenResponsesProviderAdapter
├─ LocalNativeProviderAdapter
├─ VendorSdkProviderAdapter
└─ CompanyGatewayProviderAdapter
```

适合这些场景：

- 本地模型只有 `/generate` 接口
- 公司内部模型只提供私有 SDK
- 某个厂商的多模态 / 工具调用不是 OpenAI 风格
- 某个 provider 的流式事件结构完全不同

#### 5. 工具调用从“只读”升级到“可控写入”

当前工具是保守的，只做只读：

- 查知识库
- 查网页
- 查文档

后续如果想让模型执行更强动作，可以扩展：

- 创建文档
- 修改文档
- 移动 / 重命名文件
- 写入数据库
- 生成 SQL 并等待人工确认后执行
- 调业务系统接口

但这类能力必须增加：

- 权限校验
- 操作预览
- 人工确认
- 审计日志
- 回滚策略
- 工具调用限流

不能直接让模型自由写入系统。

#### 6. 更精确的模型能力配置中心

当前 `MODEL_CAPABILITIES_JSON` 已经支持覆盖能力。

后续可以做成：

- 数据库存储模型配置
- 前端模型管理页
- 每个模型独立配置：
  - provider
  - base_url
  - api_key 是否启用
  - 是否支持图片
  - 是否支持工具
  - 是否支持 Responses
  - 是否支持 reasoning
  - 最大上下文长度
  - 最大输出 token
  - 价格

这样就不用每次都改 `.env`。

#### 7. 更强的检索工具和 Agent 编排

当前工具调用只是把“只读工具”接入模型闭环。

后续可以做：

- 多工具规划
- 查询改写工具
- rerank 工具
- 文档定位工具
- 表格查询工具
- SQL 查询工具
- 多步推理 trace
- 工具调用结果缓存

这样系统会从“RAG 问答”逐步走向“知识库 Agent”。

#### 8. 前端交互升级

后续前端可以继续补：

- 粘贴图片预览缩略图
- 上传进度
- 模型能力不匹配时的明确提示
- “当前模型不支持图片，是否切换到 qwen3.7-plus / gpt-4o-mini”
- 工具调用过程提示，例如“正在检索知识库”
- Responses API 来源引用卡片
- 图片 / 文件引用在历史消息里的可回看面板

一句话总结：

```text
当前 1-7 阶段已经把模型能力兼容层的骨架、闭环和诊断都落地了。
后续高级能力不是推翻重做，而是在 adapter、capability、message_parts、tools、streaming event 这几个扩展点上继续加深。
```

第一阶段白话理解：

```text
原来：
KnowledgeBaseService 一个人干很多活
  -> 负责 RAG 检索
  -> 负责组织 prompt
  -> 负责判断 provider
  -> 负责创建 OpenAI client
  -> 负责拼 DeepSeek / Qwen 参数
  -> 负责调用模型
  -> 负责参数失败后的重试

现在：
KnowledgeBaseService 只管业务主流程
  -> RAG 检索
  -> 组织 prompt
  -> 整理回答

LLMProviderAdapter 专门管模型供应商调用
  -> 创建 / 缓存 OpenAI-compatible client
  -> 翻译 DeepSeek / Qwen 参数
  -> 调用模型
  -> 参数失败后同模型重试
```

可以把它想成：

```text
原来是一个人既当产品经理、又当厨师、又当采购、又当收银。
现在先把“厨房出餐”这件事拆给 adapter。
产品经理只管用户要什么菜、菜谱怎么组织；
adapter 负责找哪个厨房、用哪套锅具、失败了怎么重做一份。
```

所以第一阶段不是为了立刻增加新能力，而是为了把“模型供应商调用”从 RAG 主流程里拆出去。
拆完以后，后面要加本地模型、Responses API、多模态、工具调用时，就不用继续把所有特殊逻辑塞回 `knowledge_base.py`。

第一阶段落地后的调用链是：

```text
KnowledgeBaseService
  -> _resolve_model_provider() / _resolve_model_adapter()
  -> LLMProviderAdapterFactory
  -> OpenAICompatibleProviderAdapter
  -> OpenAI-compatible chat.completions.create()
```

这次重构保留了现有行为：

- provider 路由规则不变
- `MODEL_PROVIDER_OVERRIDES_JSON` 仍然生效
- `MODEL_CAPABILITIES_JSON` 仍然生效
- DeepSeek / Qwen 的 deep thinking 参数映射不变
- 扩展参数失败后仍然使用同一 provider/model 去参数重试
- `model_diagnostics.option_fallback_used` 和 `warnings` 仍然返回给前端

变化点是：

- `knowledge_base.py` 不再直接 import / 创建 `OpenAI` client
- `knowledge_base.py` 不再直接负责 provider 参数降级重试
- OpenAI-compatible 调用细节集中到 `app/services/llm_provider_adapter.py`
- 后续如果要加本地原生 SDK、千问 Responses API、多模态 adapter，可以从 `LLMProviderAdapterFactory` 后面继续扩展

第二阶段白话理解：

超短版：

```text
第一阶段拆的是：谁负责去调用模型。
第二阶段拆的是：模型流式返回的东西，应该怎么分类。

原来所有流式内容都像一个快递袋：
  -> 只写着 delta
  -> 前端只知道“这是一段文字”

现在先给每个快递贴标签：
  -> 正文：content_delta
  -> 思考：reasoning_delta
  -> 工具调用：tool_call_delta
  -> 用量：usage
  -> 诊断：diagnostics
  -> 结束：done
```

也就是说，第二阶段不是让页面立刻多显示什么，而是先把“传输通道”和“标签体系”修好。
以后模型一边输出正文、一边输出思考、一边请求工具调用时，后端能分清它们分别是什么。

```text
原来：
后端流式输出只有两种主要信号
  -> delta：给前端追加一段回答文字
  -> done：告诉前端回答结束，并带 sources / usage / diagnostics

现在：
后端内部先统一成 StreamingEvent
  -> content_delta：最终回答文字
  -> reasoning_delta：模型思考片段
  -> tool_call_delta：模型工具调用片段
  -> usage：token 用量事件
  -> diagnostics：模型诊断事件
  -> done：最终完成事件
  -> error：错误事件
```

可以把它想成：

```text
原来后端只会喊：
“来一段正文”
“结束了”

现在后端会先把所有信号分门别类：
“这是正文”
“这是思考”
“这是工具调用”
“这是用量”
“这是诊断”
“这是结束”
```

第二阶段最初的重点是先把“事件通道”修好，避免后面加 `reasoning_content`、`tool_calls`、usage 分段返回时继续往 `delta` 里硬塞。
后续第三阶段和第六阶段已经继续往上补了两块能力：

- 第三阶段把 `tool_call_delta` 接到工具调用闭环里
- 第六阶段把 `reasoning_delta`、`tool_call_delta`、`diagnostics` 接到前端折叠展示和聊天记忆里

第二阶段落地后的调用链是：

```text
KnowledgeBaseService.stream_answer()
  -> yield StreamingEvent(content_delta / done ...)
  -> routes.py::_streaming_event_payload()
  -> 转成前端兼容 SSE
  -> frontend/src/api.ts::chatStream()
```

兼容策略是：

- 后端内部使用新事件名 `content_delta`
- SSE 发给前端时仍映射成旧的 `delta`
- 前端继续按原来的 `onDelta` / `onDone` 渲染聊天
- 新增的 `reasoning_delta`、`tool_call_delta`、`usage`、`diagnostics` 事件前端已经能接收；其中 reasoning 和 tool call 会放进助手消息折叠区

所以这一步的意义是：后端先有统一事件协议，前端再按事件类型渐进展示能力。现在这条链路已经从“可扩展通道”推进到了“基础可视化”。

第三阶段白话理解：

```text
第一阶段拆的是：谁负责去调用模型。
第二阶段拆的是：模型流式返回的东西怎么分类。
第三阶段拆的是：模型如果需要查资料，应该怎么安全地叫后端工具帮忙。
```

超短版：

```text
原来：
模型只能直接回答。
它虽然能看见 RAG 拼进去的上下文，但不能主动说：
“我还想再查一下知识库”
“我还想查一下网页”

现在：
后端给模型准备了一组只读工具。
模型如果支持 tool calling，可以先请求工具。
后端执行工具，把结果再交回模型。
模型再基于工具结果生成最终回答。
```

可以把它想成：

```text
原来模型像一个坐在考场里的学生，只能看已经发到桌上的资料。
现在后端给它配了一个只读资料员。
学生可以举手说：帮我查一下知识库 / 网页。
资料员只负责查资料，不允许改文件、不允许删文件。
查完后把资料递回来，学生再组织最终答案。
```

第三阶段增强版的边界：

- 已新增 `ToolRegistry`
- 已新增只读工具 `search_knowledge_base`
- 已新增只读工具 `search_web`
- 非流式 `/api/chat` 已接入 tool calling 循环
- 流式 `/api/chat/stream` 已接入 tool calling 循环
- 最多执行 2 轮工具调用，避免模型无限循环
- 如果 provider 不支持 `tools` 参数，会自动退回普通模型回答
- 工具调用情况会写入 `model_diagnostics.tool_calls`

第三阶段落地后的非流式调用链是：

```text
KnowledgeBaseService.answer()
  -> _build_tool_registry()
  -> _chat_completion_with_tools()
  -> OpenAI-compatible tools=[...]
  -> 模型返回 tool_calls
  -> ToolRegistry.execute()
  -> role=tool 结果回传模型
  -> 模型生成最终自然语言回答
```

第三阶段增强版补上的流式调用链是：

```text
KnowledgeBaseService.stream_answer()
  -> _build_tool_registry()
  -> _stream_completion_with_tools()
  -> 第一段 OpenAI-compatible stream tools=[...]
  -> 模型流式返回 tool_calls 碎片
  -> 后端把 tool_calls 碎片拼成完整工具请求
  -> ToolRegistry.execute()
  -> 发出 tool_call_delta 事件，记录本次调用了什么工具
  -> role=tool 结果回传模型
  -> 第二段 stream 输出最终自然语言回答
```

这一步解决的是：前端主要用 `/api/chat/stream`，如果工具调用只接在非流式 `/api/chat` 上，真实聊天体验里就等于大部分时候用不上工具。
所以第三阶段增强版把流式接口也补上了。

白话理解：

```text
原来第三阶段基础版：
普通接口会用工具；
流式接口还是只会普通回答。

现在第三阶段增强版：
流式接口也会用工具。
模型先在流里吐出“我要调用哪个工具、参数是什么”的碎片；
后端把碎片拼完整；
后端执行只读工具；
再把工具结果交回模型；
最后继续用流式方式把正式回答吐给前端。
```

当前 UI 层的处理是保守的：

- 正文 `content_delta` 继续正常显示
- 结束 `done` 继续正常保存会话
- `tool_call_delta` 前端会收集到助手消息，并放进“工具调用”折叠区
- 以后如果要做“正在查询知识库...”这类过程提示，可以直接消费这个事件

这一步不是要让模型拥有“任意操作系统”的能力。
它只开放只读工具，先把工具调用闭环跑通。
后续如果要做文件编辑、删除、写入数据库这类高风险工具，必须加权限控制和人工确认。

第四阶段白话理解：

```text
第一阶段：把 provider 调用拆出去。
第二阶段：把流式事件分类。
第三阶段：让模型能安全调用只读工具。
第四阶段：让一条用户消息不再只能是一段字符串。
```

原来聊天请求只有：

```text
question: "帮我看看这个问题"
```

现在仍然保留 `question`，但旁边多了：

```text
message_parts:
  - text
  - image_url
  - file_ref
```

这样后续前端可以把“文字 + 图片 + 文件引用”一起发给后端。
后端会把它拆成两部分：

- 用文本化内容做 RAG 检索和 prompt 组织
- 对支持图片的 OpenAI-compatible provider，传 `image_url` part

如果 provider 不支持图片输入，adapter 会自动退回纯文本描述，避免聊天直接失败。

第五阶段白话理解：

```text
Chat Completions 像普通对话接口。
Responses API 更像“带工具的响应接口”。
千问部分新模型的联网搜索更推荐走 Responses API。
所以不能继续把它硬塞进 chat.completions.create()。
```

第五阶段做的是：

```text
默认：
qwen -> OpenAICompatibleProviderAdapter -> chat.completions.create()

打开 QWEN_RESPONSES_API_ENABLED=true 且启用原生联网：
qwen -> QwenResponsesProviderAdapter -> responses.create(tools=[web_search])

如果本次是流式聊天：
qwen -> QwenResponsesProviderAdapter -> responses.create(stream=True, tools=[web_search])
     -> _responses_stream_to_chat_stream()
     -> 转成系统原来能消费的 chat stream chunk
```

为什么默认关闭？

- 你当前系统的千问 Chat Completions 已经能跑
- Responses API 支持的模型范围和返回结构与 Chat Completions 不完全一致
- 直接全量切换风险太大

所以现在策略是：

```text
显式开启才走 Responses API。
Responses API 非流式成功：provider_api=qwen_responses
Responses API 流式成功：provider_api=qwen_responses_stream
Responses API 失败：自动退回 Chat Completions，并写入 warnings
```

        object 类型
        object 定义一个包含键值对的深层结构，其中 properties 定义了对象中每个键（属性）的 schema。每个 object 的所有属性均需设置为 required，且 object 中 additionalProperties 属性必须为 false。

        示例：

        {
            "type": "object",
            "properties": {
                "name": { "type": "string" },
                "age": { "type": "integer" }
            },
            "required": ["name", "age"],
            "additionalProperties": false
        }

        string 类型
        支持的参数：
        pattern：使用正则表达式来约束字符串的格式
        format：使用预定义的常见格式进行校验，目前支持：
        email：电子邮件地址
        hostname：主机名
        ipv4：IPv4 地址
        ipv6：IPv6 地址
        uuid：uuid
        不支持的参数
        minLength
        maxLength
        示例：

        {
            "type": "object",
            "properties": {
                "user_email": {
                    "type": "string",
                    "description": "The user's email address",
                    "format": "email" 
                },
                "zip_code": {
                    "type": "string",
                    "description": "Six digit postal code",
                    "pattern": "^\\d{6}$"
                }
            }
        }

        number/integer 类型
        支持的参数
        const：固定数字为常数
        default：数字的默认值
        minimum：最小值
        maximum：最大值
        exclusiveMinimum：不小于
        exclusiveMaximum：不大于
        multipleOf：数字输出为这个值的倍数
        示例：

        {
            "type": "object",
            "properties": {
                "score": {
                    "type": "integer",
                    "description": "A number from 1-5, which represents your rating, the higher, the better",
                    "minimum": 1,
                    "maximum": 5
                }
            },
            "required": ["score"],
            "additionalProperties": false
        }

        array 类型
        不支持的参数
        minItems
        maxItems
        示例：

        {
            "type": "object",
            "properties": {
                "keywords": {
                    "type": "array",
                    "description": "Five keywords of the article, sorted by importance",
                    "items": {
                        "type": "string",
                        "description": "A concise and accurate keyword or phrase."
                    }
                }
            },
            "required": ["keywords"],
            "additionalProperties": false
        }

        enum
        enum 可以确保输出是预期的几个选项之一，例如在订单状态的场景下，只能是有限几个状态之一。

        样例：

        {
            "type": "object",
            "properties": {
                "order_status": {
                    "type": "string",
                    "description": "Ordering status",
                    "enum": ["pending", "processing", "shipped", "cancelled"]
                }
            }
        }

        anyOf
        匹配所提供的多个 schema 中的任意一个，可以处理可能具有多种有效格式的字段，例如用户的账户可能是邮箱或者手机号中的一个：

        {
            "type": "object",
            "properties": {
            "account": {
                "anyOf": [
                    { "type": "string", "format": "email", "description": "可以是电子邮件地址" },
                    { "type": "string", "pattern": "^\\d{11}$", "description": "或11位手机号码" }
                ]
            }
        }
        }

        可以使用 $def 定义模块，再用 $ref 引用以减少模式的重复和模块化，此外还可以单独使用 $ref 定义递归结构。

        {
            "type": "object",
            "properties": {
                "report_date": {
                    "type": "string",
                    "description": "The date when the report was published"
                },

## 本次补充：模型身份、诊断信息、静默降级提示

这次改动解决三个容易误判的问题：

1. 问“你是什么模型”时，不再让模型自己猜。
2. 每次回答都返回后端真实的模型调用诊断。
3. 如果 provider 不接受某些扩展参数，后端仍然会重试，但会把 warning 返回给前端。

### 1. 为什么不能只问模型“你是谁”

模型正文里的自我介绍不一定可靠。

原因是：

- 模型不知道后端最终怎么路由请求
- 模型可能根据训练语料自称某个身份
- 多 provider 兼容 OpenAI 接口时，模型自我认知和后端实际调用不一定一致

所以现在项目里如果用户问：

- 你是什么模型？
- 当前模型是什么？
- 你是不是千问？
- 你是不是 DeepSeek？

后端会直接返回实际路由信息，而不是让模型自由发挥。

代码位置：

- `app/services/knowledge_base.py::_is_model_identity_question()`
- `app/services/knowledge_base.py::_build_model_identity_answer()`

### 2. 每次回答新增 `model_diagnostics`

现在每次 `/api/chat` 和 `/api/chat/stream` 的最终返回都会带：

```json
{
  "model_diagnostics": {
    "requested_model": "qwen-max",
    "provider": "qwen",
    "resolved_model": "qwen-max",
    "native_web_search_used": true,
    "external_web_search_used": false,
    "thinking_mode": "deep",
    "option_fallback_used": false,
    "warnings": []
  }
}
```

字段含义：

- `requested_model`：前端请求的模型，例如 `qwen-max`
- `provider`：后端推断出来的供应商，例如 `qwen` / `deepseek`
- `resolved_model`：供应商最终返回的模型名
- `native_web_search_used`：这次是否给模型传了原生联网参数
- `external_web_search_used`：这次是否用了后端自己的外部搜索
- `thinking_mode`：这次是 `quick` 还是 `deep`
- `option_fallback_used`：扩展参数失败后，是否发生了去参数重试
- `warnings`：本次调用的诊断提示

前端会在助手消息下面展示一行摘要，例如：

```text
model: qwen-max | tokens in/out/total: 1752/84/1836 | provider=qwen, requested=qwen-max, resolved=qwen-max, nativeWeb=on, externalWeb=off, thinking=deep
```

### 3. 静默降级改成“可见 warning”

以前的逻辑是：

```text
第一次请求
├─ 带 enable_search / enable_thinking / reasoning_effort 等扩展参数
└─ 如果失败
   └─ 后端去掉扩展参数，再用同一个 provider/model 重试
```

这个逻辑的好处是用户不会因为某个参数不兼容而完全失败。

但坏处是：

```text
界面显示：联网开启 / 深度思考
实际可能：扩展参数失败后已经被去掉
```

现在保留“同模型重试”，但不再静默。

如果发生这种情况，`model_diagnostics` 会变成：

```json
{
  "option_fallback_used": true,
  "warnings": [
    "模型扩展参数调用失败，后端已使用同一 provider/model 去掉扩展参数重试；本次回答的原生联网或深度思考可能没有生效。"
  ]
}
```

这样就能明确知道：

- 不是切到 DeepSeek 了
- 还是同一个 provider/model
- 但联网或深思参数可能没有真正生效

### 4. 当前推荐判断方式

以后判断一次回答到底用了什么能力，不要只看模型正文，而是看三个地方：

```text
助手消息正文
├─ 只看最终回答内容

消息下方模型摘要
├─ 看 model / token / provider / nativeWeb / thinking

warnings
└─ 看是否发生扩展参数降级
```

如果要更稳定地验证“联网”，推荐优先看：

- `native_web_search_used`
- `external_web_search_used`
- `option_fallback_used`
- `warnings`

如果需要可控的网页引用，还是建议后续接入 Serper / Tavily 这类外部搜索，因为模型原生联网是供应商内部黑盒，后端不一定能拿到结构化来源。

## 第六阶段：把模型能力“看得见”

前面几阶段已经把模型调用链路拆开了，但如果前端不展示这些信息，很多能力其实还是“黑盒”。所以第六阶段的重点，不是继续加新的模型能力，而是把已经存在的能力显式展示给用户和开发者看。

### 这一阶段要让前端看见什么

现在一条助手消息里，前端可以逐步看到这些信息：

- `provider_api`：这次到底走的是 `chat_completions`、`qwen_responses` 还是 fallback。
- `reasoning_delta`：如果模型真的吐出了思考过程，前端可以把它单独收起来。
- `tool_call_delta`：如果模型触发了工具调用，前端可以知道调了哪个工具、参数是什么。
- `usage`：token 用量继续保留。
- `warnings`：如果后端发生了静默降级、工具失败、兼容性回退，前端会显示提示。

这一步的意义很直接：以后你排查“为什么这个模型看起来开了深度思考，但回答里像没开”时，不用只看模型正文，而是能看诊断条。

### 这一阶段对应的代码变化

前端主要改了三处：

1. `frontend/src/composables/useChatWorkspace.ts`
   - 接住流式事件里的 `reasoning_delta`、`tool_call_delta`、`usage`、`diagnostics`
   - 把诊断信息塞进 `UiMessage`

2. `frontend/src/components/chat/MessageItem.vue`
   - 给助手消息加一条轻量诊断条
   - 把思考片段和工具调用放进折叠区域
   - 不把这些信息做成重型调试面板，尽量保持聊天区整洁

3. `frontend/src/i18n/messages.ts`
   - 补充中英文文案

这次增强后还补了两条闭环：

4. `app/services/knowledge_base.py` + `app/api/routes.py` + `app/services/chat_memory.py`
   - provider 流式返回里的 `reasoning_content` 不再被跳过
   - 后端会转成 `reasoning_delta`
   - 最终 `done` 事件会带 `reasoning_parts`
   - 会话保存时写入 `meta_json.reasoning_parts`
   - 刷新历史消息后，前端还能重新看到这些思考片段

5. `frontend/src/components/chat/ChatComposer.vue` + `frontend/src/composables/useChatWorkspace.ts`
   - 聊天输入框新增轻量“引用”入口
   - 可从当前文档库选择文件，生成 `file_ref`
   - 可输入图片 URL，生成 `image_url`
   - 发送时统一进入 `message_parts`
   - 用户消息会回显已发送的引用 chip

### 这一阶段和前面阶段的关系

这一阶段不是在替代前面的 1-5 阶段，而是在前面基础上“把结果显出来”：

- 第一阶段负责把 provider 抽成适配层
- 第二阶段负责把流式事件统一成标准事件
- 第三阶段负责工具调用循环
- 第四阶段负责多模态 message part
- 第五阶段负责千问 Responses API adapter
- 第六阶段负责把这些能力在前端可视化

换句话说，第六阶段是在告诉系统：

> 这些能力不是只在后端跑过了就算完成，前端也要能看见它们发生了什么。

## 第七阶段：模型能力自动匹配与降级

前面几阶段已经把“能不能调用模型”“能不能流式”“能不能调工具”“能不能走 Responses API”都接上了。
但还缺一层更像生产系统的能力：**不是所有模型都支持同一组能力，后端不能默认所有模型都能吃图片、调工具、走 Responses API。**

### 这一阶段解决什么问题

如果没有模型能力匹配，会出现几类很别扭的问题：

```text
用户传了图片 URL
  -> 后端直接按 image_url part 发给模型
  -> 但模型其实不支持视觉输入
  -> provider 报错，再降级重试

模型不支持 tool calling
  -> 后端仍然传 tools=[...]
  -> provider 报错，再退回普通回答

千问某个模型不支持 Responses API 或 Responses 流式
  -> 后端仍然硬走 responses.create()
  -> 报错后再退回 chat.completions
```

这样虽然最终可能还能回答，但体验不好，诊断也不够清楚。

第七阶段做的是把这些能力放进统一的 `ModelCapability`：

```python
supports_native_web_search: bool
supports_tool_calling: bool
supports_multimodal_input: bool
supports_responses_api: bool
supports_responses_streaming: bool
thinking_style: Literal["none", "deepseek", "qwen"]
```

### 当前默认能力

当前默认策略是保守的：

- DeepSeek：默认支持工具调用，不默认支持原生联网、图片输入、Responses API。
- Qwen：默认支持原生联网、工具调用、Responses API 和 Responses 流式；图片输入不是所有 Qwen 都默认打开，而是按模型名自动识别 `qwen-vl*`、`qwen-omni*`、`qwen3.7-plus`、`qwen3.7-max` 等视觉/多模态模型，避免把普通文本模型都当成视觉模型。
- OpenAI：`gpt-4o*`、`gpt-4.1*`、`gpt-5*`、`o3*`、`o4*` 默认标记为支持图片输入。
- 其他 provider：默认是通用 OpenAI-compatible，能力不开太多，需要时通过覆盖配置打开。

如果某个模型能力和默认值不同，可以在 `.env` 里用 `MODEL_CAPABILITIES_JSON` 覆盖，例如：

```env
MODEL_CAPABILITIES_JSON={"gpt-4o*":{"supports_multimodal_input":true},"local-*":{"supports_tool_calling":false,"supports_native_web_search":false}}
```

这里支持精确模型名，也支持 `*` 前缀匹配。

### 结合当前 `.env.example` 默认模型看，哪些模型支持什么

注意这里分两层：

1. **系统声明能力**：后端 `ModelCapability` 现在会怎么处理。
2. **官网真实能力**：供应商文档说这个模型/系列能不能看图、调工具。

当前默认模型列表里，按系统声明能力可以这样理解：

| 模型 | provider | 工具调用 | 图片输入 | 说明 |
| --- | --- | --- | --- | --- |
| `deepseek-v4-flash` / `deepseek-v4-pro` | `deepseek` | 默认开启 | 默认关闭 | 默认走 DeepSeek 风格推理参数；如果实际模型不支持 tools，可用 `MODEL_CAPABILITIES_JSON` 关闭 |
| `glm-4.5-air` | `zai` | 默认开启 | 默认关闭 | 当前按通用 OpenAI-compatible 处理 |
| `hunyuan-lite` | `hunyuan` | 默认开启 | 默认关闭 | 通过 `MODEL_PROVIDER_OVERRIDES_JSON` 映射到混元 |
| `gpt-4o-mini` | `openai` | 默认开启 | 默认开启 | OpenAI 视觉模型系列，系统会自动标记图片输入 |
| `kimi-k2.6` | `kimi` | 默认开启 | 默认关闭 | 当前按通用 OpenAI-compatible 处理 |
| `qwen-max` | `qwen` | 默认开启 | 默认关闭 | 千问文本/通用模型，系统不把它默认当视觉模型 |
| `qwen3.7-plus` | `qwen` | 默认开启 | 默认开启 | 百炼文档里的图像输入示例可以用它，系统已按视觉模型识别 |
| `qwen-vl*` / `qwen-omni*` | `qwen` | 默认开启 | 默认开启 | 千问视觉/多模态系列，系统按前缀自动识别 |

所以你问“千问应该可以吧”：是的，但要精确到模型。
`qwen3.7-plus`、`qwen-vl-plus` 这类可以按图片模型处理；`qwen-max` 这类不建议系统默认硬开图片输入，除非你确认当前账号/模型版本支持，再用 `MODEL_CAPABILITIES_JSON` 覆盖。

如果你想在本地 `.env` 里显式打开，可以这样写：

```env
AVAILABLE_MODELS=deepseek-v4-flash,deepseek-v4-pro,gpt-4o-mini,qwen-max,qwen3.7-plus,qwen-vl-plus
MODEL_PROVIDER_OVERRIDES_JSON={"gpt-4o-mini":"openai"}
MODEL_CAPABILITIES_JSON={"qwen3.7-plus":{"supports_multimodal_input":true},"qwen-vl*":{"supports_multimodal_input":true},"gpt-4o-mini":{"supports_multimodal_input":true}}
```

这里的 `MODEL_CAPABILITIES_JSON` 不是必须每次都写，因为系统已经内置了一些常见视觉模型识别；它的价值是当供应商模型列表更新、或者你接入私有模型时，可以不用改代码就覆盖能力。

### 为什么前端直接粘贴图片，后端字段还叫 `image_url`

这个问题很容易误解：

```text
用户视角：
  我是直接 Ctrl+V 粘贴了一张截图，不是输入 URL。

协议视角：
  OpenAI-compatible 多模态消息里，图片 part 的字段名就叫 image_url。
```

也就是说，`image_url` 是协议字段名，不等于“用户必须手动输入一个 URL”。
它可以放两类值：

```text
1. 真实 URL：
   https://example.com/a.png

2. data URL：
   data:image/png;base64,iVBORw0KGgo...
```

所以当前系统的处理是：

```text
Ctrl+V 图片
  -> 前端读取剪贴板 File
  -> 转成 data URL
  -> 塞进 message_parts[].image_url
  -> 后端看到这是 image_url part
  -> 如果模型支持图片，就原样传给 provider
  -> 如果模型不支持图片，就只把它降级成“用户粘贴了一张图片”的文本摘要
```

为什么不直接把本地文件路径传给后端？

- 浏览器拿不到稳定、可让云模型访问的本地文件路径。
- 云模型也访问不了你电脑上的 `C:\xxx\image.png`。
- 所以要么用 data URL，把图片内容直接放进请求；要么上传到后端/对象存储，再生成 URL。

当前选择 data URL，是因为它最适合本地快速体验：用户不用管上传，也不用找公网图片地址。
但它的缺点也明确：

- 图片太大会让请求体变大，所以前端限制了 2MB。
- 某些 provider 可能不接受 data URL，只接受公网 URL。
- 如果要长期保存图片或给云模型稳定读取，后续应该做“上传图片 -> 存储 -> 生成 URL”的正式资源管理。

参考依据：

- 阿里云百炼“选择模型”页面说明百炼覆盖文本、图像、音频、视频等多种模态，并把 `qwen3.7-plus` 放在“图像与视频 / 理解”能力下：https://help.aliyun.com/zh/model-studio/models
- 阿里云百炼“函数调用”页面说明 Assistant API 支持 Function Calling，并展示 `tools=[...]`、函数 schema、提交工具输出的流程：https://help.aliyun.com/zh/model-studio/function-calling
- OpenAI Images and vision 文档说明图片输入既可以是完整图片 URL，也可以是 Base64 data URL；Chat Completions 示例里字段名仍然是 `image_url.url`：https://platform.openai.com/docs/guides/images

### 运行时怎么降级

这一阶段不是只在前端展示几个标签，而是后端真的会按能力处理：

1. 图片输入
   - 如果 `supports_multimodal_input=true`，图片 URL 会作为 OpenAI-compatible `image_url` part 传给 provider。
   - 如果 `supports_multimodal_input=false`，图片 URL 会降级成普通文本引用，并写入 `model_diagnostics.warnings`。

2. 工具调用
   - 如果 `supports_tool_calling=true`，后端才会进入 `ToolRegistry` 工具调用闭环。
   - 如果 `supports_tool_calling=false`，后端直接跳过工具调用，普通模型回答，并写 warning。

3. 千问 Responses API
   - 如果 `supports_responses_api=true`，并且 `QWEN_RESPONSES_API_ENABLED=true`，千问原生联网才优先走 `responses.create()`。
   - 如果流式请求还要求 `supports_responses_streaming=true`。
   - 如果能力不满足，会回到 Chat Completions 兼容接口，并在 warning 里说明原因。

4. 本地工具和千问原生联网的关系
   - 当千问开启 Responses API 且本次使用原生联网时，后端会优先走千问 Responses API 自带的 `web_search`。
   - 这种情况下不会再同时塞入本地 `ToolRegistry` 的 `tools`，避免两个工具体系抢同一个请求通道。

### 前端能看到什么

模型健康检查弹窗现在除了原来的 API Key、Base URL、原生联网、思考映射，还会展示：

- 工具调用
- 图片输入
- Responses
- Responses 流式

助手消息的诊断信息里也会带 `capabilities` 快照，后续如果要做更细的 UI 提示，可以直接基于这个字段判断。

白话理解：

```text
前几阶段是把各种能力接到车上。
第七阶段是给每辆车贴“准驾车型”。

这辆车能不能上高速？
能不能拖挂？
能不能载货？
能不能走专用通道？

能就用；
不能就换普通路走，并告诉你为什么换路。
```
